## 2. 核心变化：能力知识从「报告里的表格」变成「跟着检查点走的档案」

```
./.venv-cuda/Scripts/python.exe laya_bridge.py capability          # 生成（不跑模型，秒级）
./.venv-cuda/Scripts/python.exe laya_bridge.py capability --check  # 核对现有档案是否仍与磁盘一致
```

三条设计约束（每条都有理由，不是洁癖）：

1. **等级不在这里定**。全部读 `tests/runs/*.json` 里 `signalmetrics` 已经算好的 `grade`。
   想改判据只能改 `grade_signal()` —— 改在档案层等于偷偷改评分规则。
2. **status 推导规则写死在代码里**（`_derive_status()`，可审计）。
   唯一例外是 config 里 `capability_policy.override` 显式点名的 signal，
   档案会标 `status_source=policy_override` 并附理由 —— 覆盖是**可见的**，不伪装成推导结果。
3. **档案必须能自证来源**：五类哈希。`dataset` / `checkpoint` / `config` / `translation_cache`
   不符 → **硬阻断**（拒绝产出状态增量）；`code` 不符 → **只提示**（`code_changed`）。
   硬阻断只留给**输入侧**：输入变了，同一份档案描述的就是另一批条件，没有辩解空间。

status 推导表：

| status | 条件 | 含义 |
|---|---|---|
| `active` | `grade=A` | 该 role 的主输入；`role=state_shift` 时才能产生状态增量 |
| `auxiliary` | `grade=B` / `grade=C` | 只能当合取/修正项 |
| `disabled` | `grade=D` / `N` / 跑次等级不一致 | 不接入正式链路 |
| `semantic_review` | `grade=R`（稳定反向） | 方向/语义有问题；**禁止静默取反** |

★ **`portability`（跨检查点稳定/特有/反向）刻意不参与降级。**
档案是按检查点生成的：拿另一个检查点的表现否定当前检查点，
等于让 A 条件的数据否定 B 条件的实验。它只写进 `revalidate_on_switch`；
安全阀是「换检查点必须重新生成档案，哈希对不上直接拒用」。

## 4. 与提示词的差异（我主动改严的地方，需要你裁决）

1. **`auxiliary` 更严**：提示词说「只能在合取/修正中作辅助项」。
   我的实现是——**P2 阶段 `auxiliary` 对会写状态的量不产生任何数值效果**，
   只登记「若启用会产生多少」（`applied: false`）。理由：会写状态的量一旦算错是**不可逆**的
   （对比：行为选错，下一轮还能改）。
2. **`proposed_deltas` 语义变了**：它现在等于**过滤后**的结果，未过滤的全量移到
   `raw_deltas_all_signals`（仅供审计、无写入权限）。旧前端只读 `proposed_deltas`，
   所以行为会变（例如 td 上从 6 条变成 3 条）——**这是预期的**，但属于破坏性变更，需要知情。
3. **档案不可用时不退回默认**：未登记的检查点（如 `multilingual`）→ `load_capability_profile()`
   返回 `None` → **0 条状态增量**，而不是「全都可用」。代价是那个检查点上桥不再给状态建议。
4. **`doubt` 的口径冲突已记录、未擅裁**：提示词把 `doubt` 归入 `situation_assessment`，
   而 `state_proposal` 的字段示例里也出现了 `doubt`。但状态侧真正写 `relationship.doubt` 的是
   `doubt_shift`；`doubt` 是 `prob` 型、在 `state_shift.paths` 里**没有条目**。
   我按提示词的显式清单把 `doubt` 标为 `situation_assessment`，
   加 `_collision_note` 说明同名不同义，**没有**给它造一条通往 `relationship.doubt` 的路径。

## 5. 请重点质疑的地方

1. **★ 等级判据本身没动，所以档案只是把既有判据「系统化」了。**
   如果 `grade_signal()` 的判据有系统偏差（比如 CI 口径、噪声底 0.05 沿用旧实测值），
   档案会把这个偏差**固化进生产链路**——从「报告里写错一句」升级成「代码按错的来」。
   这条我认为是最需要外力检查的。
2. **两条 `policy_override` 是人写的，不是数据推的。** 虽然可见且带理由，
   但它意味着档案里不是 100% 自动生成。`investigate`（判别力最高却方向反）和
   `disclose`（td D / en A，符号翻转）这两条，若你认为应该由数据决定，需要重新讨论。
3. **`investigate` 的两种解释仍未裁决**（用例期望写反 vs 信号语义其实是「信息缺口」）。
   本轮**没有**改名、**没有**取反、**没有**给它任何阈值——但也没有解决它。
   若要查清，需要单独设计一组「信息充分 / 不充分」的用例，这是新实验，不是调参。
4. **档案只覆盖两个检查点**，`multilingual` 未跑。若 P2 的结论要外推到「所有 Laya 检查点」，
   样本量是 2，不够。
5. **6 个 `*_shift` 没有 contextual 配对用例**（同一句话换前文时，score 位移题不构成配对），
   所以它们的「最终等级」事实上只由判别力决定。这是**已知限制**，写在 config 的 `_note` 里，
   但它意味着 `trust_shift` 的 A 级**只被验证了「能不能分开两类输入」，没被验证「会不会随前文变」**。
6. **`contextual` 组样本偏薄**：`confront` 配对 n=1、`danger` n=10、`investigate` n=10。
   这些维度上的等级（尤其 `confront` 的 C 和 `investigate` 的 R）证据强度弱于 `doubt`(n=25)。
7. **`portability` 依赖 `tests/ckpt_replication.json`**（`ckpt_analysis.py` 的产物）。
   该文件不在时，档案会标「未跨检查点验证」而**不报错** —— 这是个软依赖。
   我刻意没有在桥里重写一遍 `classify()`（两份规则一定会漂），但代价是这条隐性耦合。
8. **阈值仍然全部未标定**：`metrics.best_threshold_median` 只是统计输出，
   档案里显式标了 `best_threshold_is_statistical_only: true`，**没有**回写 config / Policy。
   所以「Behavior Tendency 该怎么分档」这个问题**本轮没有答案**，
   我刻意让 `behavior_tendency` / `situation_assessment` 两块只给值、不判读。
9. **`code_changed` 这个软提示可能被无视**：任何对 `laya_bridge.py` 的改动都会让它变 True，
   而它**不阻断**。如果有人改了判据又没重跑 `capability`，档案会继续被用。
   我选了「不阻断」是因为硬阻断会让每次改注释都要求重跑，最后一定被绕过——
   但这是个**权衡**，不是显然正确的选择。

## 6. 现状判定与下一步

**现状**：Laya 依然是**NPC 状态变化 + 行为倾向的快速推演器**（定位未变）。
P2 加的不是新能力，而是**权限边界**：
- 只有该检查点上已验证（`role=state_shift` + `status=active`）的信号才会产生状态增量；
- 其余全部逐条留原因地被拦下；
- Laya 的输出仍只是 Proposal（`is_proposal=true` / `authority=none`），不写 Actor State。

**下一步（P3 之前必须先做，且本轮刻意没做）**：
1. 用 `trust_shift` 做 **State Transition 端到端验证**（Proposal → Validate → Transition → Commit）。
2. `disclose` / `investigate` 的语义裁决需要新用例集，不是调参。
3. 若要外推「所有检查点」，至少再跑一个检查点。

**P2 到此为止，不自动进入 P3。**
