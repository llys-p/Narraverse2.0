## 2. 掉档不是模型退化 —— 是「翻译措辞」这个从未被测量的量

| **137 条英文译文** | 旧缓存 | **新缓存** | ★ **变了** |

### 2.2 量化：`temperature=0.0` **不等于**确定性

脚本：`tests/replication/xlate_drift.py`（判据看结果前固定）。
对缓存里的中文再翻一次：

| 30 句样本 | 数量 |
|---|---|
| 逐字一致 | 4（**13%**） |
| 近似（相似度 ≥0.90） | 8 |
| **明显不同（<0.90，最低 0.50）** | **18（60%）** |

13% ≤ 预设判据 40% → **判定「重译不可复现」**。

**这推翻了一个长期隐含假设**：旧 `run1/run2/run3` 的**位级一致**，
不是「模型 deterministic」，而是「**英文输入被冻结**」。

### 2.3 第二重证据：CI 宽度本来就横跨 A/C 边界

```
typed-decisions__p3r2.json      auc=0.8267  CI=[0.639, 0.971]  宽度=0.332  → A
typed-decisions__p3p2r1.json    auc=0.7300  CI=[0.478, 0.912]  宽度=0.434  → C
```

`trust_shift` 只有 `n_high=15` / `n_low=10`，CI 宽 **0.33~0.44**。
点估计从 0.827 移到 0.730，`ci_low` 从 0.639 落到 0.478 —— **跨过 0.50 这条判据线**。

→ **A 与 C 的分界本就在噪声内。等级由措辞决定，不由能力决定。**

## 3. 后果：一个「没接线」的失败，伪装成 10 项失败

档案规则：**只有 `role=state_shift` 且 `status=active` 才写 Actor State**。
`trust_shift` / `fondness_shift` 掉到 C → `auxiliary` → **拒绝写**。
可写信号：`[trust, doubt, fondness]` → **`[doubt]`**。

```
p3_experience（typed-decisions）
  合计 16 项：6 PASS / 10 FAIL
  全部 commit 的 signal 分布: {'doubt_shift': 50}   ← 50 次 commit 全是 doubt
  trust 全程恒为 60（模板初值）                     ← 一次都没被写过
  fondness 应升/应降 两组净变化均 0.0000
```

### ★★ 最容易骗人的地方：两个 PASS 是**假通过**

| 判据 | 显示 | 真实情况 |
|---|---|---|
| **E3** 中性聊天不漂移 | **PASS** | trust **根本没被写过** → 「不漂移」是必然的，**零证据价值** |
| **N1** 10 轮闲聊不漂移 | **PASS** | 同上 |

这两条测的是「关系不漂移」，而当前关系**没有任何写入通路**。
**只看 `n_pass=6` 会误判成「基本可用」，实际是「只有 doubt 在工作」。**

其余 FAIL 全部同源：没有 commit 通路 → 不累积、方向不可测、维度无从观察。

## 4. 顺带修掉的一个真 bug（真机撞到，非本轮引入）

`/decide`、`/turn`、`/commit` 在写历史日志时用了 **`out["engine"]` 下标取值**。
但 `decide()` 有**两条返回路径**：

- 正常轮 → 带 `engine` / `device` / `routing` / `answers` …
- **fail-closed 轮（翻译失败）→ 精简返回，没有 `engine` 键**

→ `KeyError: 'engine'` → `BaseHTTPRequestHandler` 抛异常 → **HTTP 连接被掐断**
（客户端看到 `ConnectionRefusedError 10061` / `RemoteDisconnected`）。

**症状极具误导性**：表现为「桥挂了」，实际是「一个可控的干净拒绝把路由打崩了」。
这正是 fail-closed 改造**放大**出来的次生问题 —— 之前失败会回落中文继续跑，
所以永远走不到那条精简返回路径。

修法：两处改 `out.get("engine")`。T10 钉住两条独立事实：
① 源码里 `"engine": out.get("engine")` 恰好 2 次、不得有下标形式；
② fail-closed 返回**确实不含** `engine`/`decision`/`turn`。

★ 通用教训：**函数有多条返回路径时，共享的消费代码一律 `.get`，不要下标。**

## 5. 为什么不继续跑 `p3p2_playthrough` / `p3p2_acceptance`

用户给的通过条件：
> 「若正常 30–50 轮试玩没有明显关系暴涨、乱漂、串 NPC、错误 commit，就通过这一阶段。」

**「6 PASS / 10 FAIL、trust 一动不动」不满足这个条件** ——
它既不是「没有明显异常」，也不是「明显异常」，而是**根本测不到**：
状态层按设计拒绝写入，试玩 30–50 轮得到的仍然只是「关系恒为初值」。

因此在当前档案下那两个脚本的结论是**预定的**，跑它们只是为已知结果烧 30+ 分钟 CPU。

**已停在此处，不进 Personality / Relationship Stage / Memory / Behavior Tendency。
也没有调任何参数**（改 `grade_signal` 阈值 / 放宽死区 / 改 `max_tokens` 都属凑参数，禁止）。

## 6. 三条出路（需用户裁决）

| 选项 | 内容 | 代价 / 风险 |
|---|---|---|
| **A. 接受现状** | 只宣布 `doubt_shift` 可用；trust/fondness 明确降级为**观察项**；Phase2 缩水交付 | 「关系只有怀疑在动」，玩法受限；但档案诚实 |
| **B. 冻结缓存 + 纳入版本控制**（推荐） | `cache_frozen` 写进铁律；**把 `_diag/translation_cache.json` 提交进 git**；此后等级以该缓存为准 | 需用户同意缓存入库；`trust_shift` **仍是 C**，不会回到 A |
| **C. 复现旧缓存** | — | **不可行**：旧英文已不可再生 |

★ **三者都不会让等级回到 A。** 差别只在于「要不要承认并制度化这件事」。
