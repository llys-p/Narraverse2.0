# Laya 定位书：Narraverse 轻量判断引擎

更新时间：2026-09-24 18:40

状态：记录本轮已确认的产品方向；第一版范围及实现约定为建议默认值。本文不是实现完成或验收通过的声明，也不是 Narraverse 正式接入契约。

## 1. 产品目标

Laya 根据对话、已发生事件、当前角色状态和必要上下文，提供有限范围的结构化判断，让角色在互动中呈现连续的情绪和关系变化。

云端大模型负责故事方向、人物表达、开放式剧情决策，并提出初始人物数据；状态系统校验、保存初值和后续变化；Laya 提供变化判断和反应倾向。

目标体验：玩家说出一句话，能够看到角色的即时反应信号；云端收到最新状态和相关信号，写出符合人物与剧情的回复。响应速度、判断质量和对回复的实际帮助，均由 Demo 验证。

## 2. 职责分工

| 组件 | 职责 | 输出权限 |
|---|---|---|
| 云端大模型 | 建立人设与故事方向、提出初始数据、理解复杂剧情、选择行动、生成回复 | 可提出初始化和剧情事件；生成文本本身不直接覆盖权威数值 |
| Laya Analyzer | 判断目标角色的情绪、关系变化方向、有限反应倾向 | 产生结构化建议，不直接执行剧情行动或修改状态 |
| State Manager / Store | 校验初值、把判断映射为有限数值变化、提交、保存、提供最新快照 | Demo 内唯一状态写入入口；正式接入时服从 Narraverse 已有状态所有权 |
| 普通规则代码 | 金币收支、确定伤害、上下限等明确计算 | 在状态系统中按规则执行，无需经过 Laya 猜测 |
| 提示词适配层 | 把状态与信号转成云端可理解的背景、约束和表现参考 | 影响生成方式，不代替提交、去重和数值校验 |

Laya 继续读取人设摘要、当前状态和必要上下文，但不独立组织 NPC 目标、复杂行动计划或 Agent 行为链。

## 3. 一轮互动的顺序

```text
云端提出初始人物数据 → 状态系统校验并保存
                              ↓
玩家消息 / 已确认发生的事件 + 当前状态 + 必要上下文
                              ↓
                         Laya Analyze
                              ↓
              结构化判断 + 可选反应倾向
                              ↓
           State Manager 校验并 Commit 有效变化
                              ↓
       最新状态 + 本轮变化 + 原始对话 + 人设与世界观
                              ↓
                    云端大模型生成回复和剧情
                              ↓
                          下一轮互动
```

- 玩家已经发出的对话可成为本轮判断依据；对话中声称的事情不自动成为世界事实。
- “准备送礼”“想去酒馆”是意图，不等于送礼或移动已经发生。
- 云端回复中新增的剧情结果，经过确认后作为后续事件处理；同一事件只能记一次。
- 第一版先聚焦玩家对话引起的反应；复杂剧情事件抽取与确认机制后续设计。
- 下一轮仍读取最新状态。移除的是 Laya 的自主行动决策职责，不是上下文和状态反馈。

## 4. 保留即时反应体验

保留逐轮观察情绪和反应倾向的面板，不把所有有趣的反应压缩成关系数值。

三类信号的含义必须区分：

| 信号 | 含义 | 第一版建议 |
|---|---|---|
| 情绪 | 目标 NPC 当前受到的情绪影响 | 核心展示；可靠时可更新情绪状态 |
| 信任变化 | 目标 NPC 对当前玩家的信任变化 | 核心候选；通过验证后才开放写入 |
| 反应倾向 | 更倾向追问、回避、解释、安慰等 | 可选观察项，给云端参考，不强制执行 |

好感度是后续关系维度；第一版不因保留旧面板而宣称其已可用。场景切换、秘密披露和调查执行由剧情层负责。Safety、长期人格成长、复杂记忆和世界模拟不纳入本轮。

未经校准的模型输出称为“分数”或“倾向”，不能直接称为真实行动概率。归一化熵、分类概率、数值强度和可靠性也不能混为一个 confidence。

## 5. 判断对象与最小输出

默认对象：目标 NPC 对当前玩家的关系，以及目标 NPC 本身的情绪。必须绑定会话和角色；多角色之间不得串用状态。

例如玩家说“你骗了我吧”，能直接看出的是玩家的怀疑；NPC 可能紧张、委屈、生气，也可能平静。不能把玩家的情绪直接存进 NPC。

建议先判断信任“上升 / 不变 / 下降 / 无法判断”，再由固定规则映射为有限 delta。初版可试用 -1 / 0 / +1；具体幅度是待验证的游戏规则，不是模型测得的客观心理量。

面向页面的最小业务结果示例：

```json
{
  "trust_delta": -1,
  "emotion": "wary"
}
```

信息不足时允许：

```json
{
  "trust_delta": null,
  "emotion": "unknown"
}
```

- `0` 表示判断无变化，`null` 表示无法判断；后者不产生该字段的更新。
- `unknown` 不覆盖已有情绪。候选标签和含义在实现时统一，不混用近义字段。
- 无法判断是正常结果；翻译失败、模型异常是错误状态，两者需在接口元数据中区分。
- 行动倾向可单独作为可选字段展示；不要求第一版一定产生倾向，也不为凑齐字段编造值。
- 技术层仍需分析编号、状态版本等提交信息；固定 schema 由适配层保证，不要求 Laya 自行写 JSON 或文学理由。

## 6. 状态提交的最低要求

1. Analyze 不改变角色状态和已提交事件历史；可以保存待提交的分析记录。
2. Commit 绑定分析编号、会话、角色及分析时的状态版本；重复提交同一结果不重复加减。
3. 当前状态已变化时，旧分析结果拒绝直接提交，重新分析或显式处理冲突。
4. 状态更新与该次更新记录一致；页面只展示服务端返回的已提交快照。
5. 每项变化独立校验；不可用信号不因其他信号通过而获得写入权限。
6. 第一版界面保留手动 Commit，方便观察；后续自动提交复用同一入口。
7. 云端生成失败时展示明确状态，重试回复不得再次应用本轮 delta。是否撤销已发生互动由显式操作决定。

简化接口方向：`/analyze` 返回分析编号、基础状态版本和建议；`/commit_state` 只接受 `analysis_id + expected_state_version`，从服务端 Pending 取回已验证 Proposal，不接受任意客户端 delta 作为权威数据。

最小历史记录应能追溯输入事件、变化前后状态和采用的规则。重启恢复、撤销交互与持久化方案在实现时明确，不能将现有内存记录直接宣称为完整回滚能力。

## 7. 提示词先实现的部分

现阶段允许通过提示词处理：状态区间的自然语言解释、情绪如何表现、行动倾向如何参考、保持人设和避免机械播报数值。

云端输入应区分“已提交状态”和“参考信号”，例如：

```text
已提交状态：NPC 对玩家的信任 35/100；本轮变化 -1。
当前情绪：wary。
参考倾向：更倾向谨慎回应；这不是必须执行的行为。

结合人设、原始对话和当前剧情自然回应。
状态区间按本作品的规则解释，不机械复述数值。
```

提示词可以先改善表现，但不能保证状态落盘、阻止重复提交或代替代码校验。云端若发现状态与剧情冲突，可标出问题，不能静默改写已提交数字。

## 8. Demo 页面与验证目标

页面顺序：玩家输入 → 当前角色状态 → Analyze 结果及可选倾向 → Commit 后状态 → 云端角色回复。

增加一个可展开区域，显示本轮实际发给云端的状态摘要，并标明提交状态。它用来确认数值进入了请求，而非只在页面上变化。

验证分三步：

1. **闭环成立**：少量代表性样本检查 Analyze 无写入、Commit 去重、角色隔离、下一轮读取新状态。
2. **判断有用**：逐步形成 100 条固定样本，覆盖明确正负互动、中性、否定、歧义、上下文差异；观察方向正确性、情绪对象、无法判断比例、重复输入和同义改写表现。不能用“所有变化都为零”证明不漂移。
3. **云端确实受益**：检查实际送模内容，再对少量相同对话比较不同状态，以及有无 Laya 信号时的回复。合理差异才是证据，不要求每次回复都显著不同。

速度记录应包含翻译、Laya 推理、状态处理和云端生成的分段耗时；不能用单次本地推理耗时代表整轮响应速度。具体速度门槛和准确率门槛在评价前约定，定位书不预先宣布达到。

## 9. 测试资产与既有成果

固定测试输入、经过检查的译文、期望标签或方向范围，并记录所用模型、问题模板和映射规则版本。测试期间缺译文应明确失败，不静默重译改变基线。

冻结译文保障可复现；少量固定同义表达用于观察鲁棒性。两者都需要。测试资产与日常运行缓存分开，只纳入经过检查的测试材料，不直接提交整个私人对话缓存。

保留既有模型加载、翻译适配、状态结构、变化校验和测试工具；旧行为决策链保留作历史参考，新入口不再依赖 NPC 行为被选中才能提交关系变化。

## 10. 当前实现与新方向的差距

施工基线：`laya-p2-safe` 的 `38dd466`；实际接手时重新查询当前 HEAD。以下区分仓库记录、本轮实现与尚未完成项：

- 仓库 P3P2 验收说明记录 trust/fondness 降级、体验测试 6 PASS / 10 FAIL；这些结果本轮未重跑。
- 本轮已拆出 `analyze_core()`、`validate_state_delta()` 与唯一写入入口 `commit_state()`；`/decide` 不写 Actor State，`/turn commit_state=false` 不写状态或历史，兼容 `/commit` 会从服务端 Pending 提交状态与历史。
- 新版 `/analyze`、带状态版本检查的 `/commit_state` 及一次性 `analysis_id` 尚未实现；客户端仍不能把任意 delta 当成权威提交。
- 本轮状态层回归 54/54 通过；模型 benchmark、100 条稳定性验收和云端叙事效果未复测。能力档案 worktree mismatch 仅记录、不重生成；正式协议在独立任务设计后再实现。
- 原页面仍有 `applyDeltas()` 本地加减逻辑，需要改为展示权威快照。
- 是否真正送入云端，以及云端是否按状态产生合理差异，需用新闭环验证。

证据入口：[P3P2 验收说明](给外部审查的-P3P2验收说明.md)、[桥接源码](laya_bridge.py)、[现有页面](laya-live-demo.html)。旧 README 和接入报告保留历史背景；产品方向以本文为准，已有能力以对应实验事实为准。

## 11. 已确定、建议默认与后续决策

**已确定方向：**云端承担创作与剧情决策；Laya 提供有限判断；状态系统保存权威状态；保留即时情绪与倾向体验；部分表现先通过提示词实现；现有成果复用，停止扩展自主 NPC 大脑。

**建议默认：**首版聚焦 trust 与 emotion；反应倾向作为可选观察项；人工 Commit；未知不更新；旧代码保留；新闭环独立演示，不直接进入正式 Runtime。这些是实施起点，不是已验证能力。

**后续通过实现和小规模体验确定：**标签词表、数值映射、上下文长度、提示词写法、速度与质量门槛、持久化及撤销方式。

**扩大范围时再由产品决策：**是否启用自动提交；是否加入好感等更多维度；是否允许某些倾向成为硬性行为限制；是否进入 Narraverse 正式状态与剧情链路。

目前没有阻塞本定位书成立的额外用户选择。下一步是最小闭环的实施设计，不因本文落盘自动开始代码重构或全套检测。
