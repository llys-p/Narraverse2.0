## 1. 结论与产品目标

建议采用“现有规则内核 + 场景式交互 + 有限事件推进”的 V1.5 路线。保留 World、Store、Action、Schedule、Encounter、Judgment、Facts、Settlement，补齐目前缺少的 NPC 对话、语义理解、认知过滤和跨天事件状态。

原讨论抓住了正确方向：玩家应该看到场景、人物和行动反馈。但它低估了两个问题：目前的自由输入不等于自由行动；现有规则闭环不等于已经有可持续对话与故事推进。单纯隐藏面板无法解决这两点。

本期产品目标：玩家在一个小世界里，用自然语言完成移动、寻找、交谈、观察调查、邀请、有限风险行为、等待和睡眠；行动有确定后果，人物有信息差，事件可跨天发展，刷新后能继续。玩家不介入也允许世界温和变化，但现实中不操作、关闭页面或打开管理页都不推进游戏时间。

完成标准是“能稳定玩完一个有因果关系的小故事”，不是“能无限输入任何句子并得到成功描述”。自由输入接受开放表达，实际执行受当前世界对象、地点和规则约束。

## 3. 三条路线与取舍

| 路线 | 最有力的理由 | 主要代价 | 判断 |
| --- | --- | --- | --- |
| A：仅调整 UI | 见效快，较少影响旧规则，适合先确认阅读体验 | 自由行动仍可能只记日志；时间太粗；没有真实对话与事件连续性 | 作为第一个小阶段，不作为 V1.5 完成标准 |
| B：保留内核，补齐交互与有限事件 | 已有边界清楚，能直接复用测试；同时解决可玩性与一致性 | 需要少量新增模型协议、状态字段和规则，不能当成纯换皮 | 推荐 |
| C：V2、多 Agent、Obsidian 主存储 | 长期可容纳更复杂自治世界与知识组织 | 要同时解决调度、并发写入、资料同步和存档迁移，明显扩大本期 | 延后 |

选择 B 的核心变量是“现有规则能否稳定承载小世界游玩”。如果三名 NPC、五个地点、七个游戏日都不能稳定运行，增加 Agent 数量或存储系统不会改善它。

不沿用对话中“四成复用、四成重构、两成新增”之类未经代码量与行为范围测量的比例。本方案按具体文件、接口和验收任务拆分。

## 4. 优化后的需求总纲与范围

### 本期必须交付

- 场景为主的游玩页，输入区容易找到；世界管理可进入、可返回。
- 自然语言统一入口；至少支持移动、寻找、聊天、观察／调查、帮助、邀请／说服、有限物件行为、等待、睡眠。
- 主动行为经统一规则执行；未知、歧义、不具备前提的行为能明确反馈。
- NPC 真正回应，引用自己的可知信息，有稳定性格、当前情绪和目标差异。
- 场景、对话、行动结果、可观察世界变化连续展示并保存。
- 自动加载当天安排、自动更新在场人物；世界只随游戏内行动推进。
- 少量可跨天的事件，允许介入、忽略、缓和、解决和过期。
- 玩家所知、NPC 所知、世界事实、尚未发生的计划彼此区分。
- 调用次数有上限，长卡和长期游玩不会无限增大单次输入。
- 保存失败、模型失败、重试、切换世界、刷新等情况有明确行为。

### 本期有限支持，避免承诺“任何行为都能实现”

- “去酒吧找林雨”支持移动后在场寻找；最多两个连续步骤，不自动继续替玩家聊天、偷窃或作决定。
- “调查文件／拿走文件”只针对世界中已存在、声明允许交互的场景物件；没有对象就解释缺少目标，不编造已取得物品。
- “给陈雪打电话”在本期先回答尚无远程联系能力，并提供已知的见面办法；不伪装成当面聊天。不把通讯录、电话、异步消息系统隐含塞入 V1.5。
- 世界背景先复用世界说明与少量显式选定资料；保留现有角色来源。自动从任意大型世界书生成地图、势力和所有物件属于后续需求。
- 保留早／中／晚，不虚构“18:20”这样的分钟精度。
- 首轮验收目标为 3 个 NPC、5 个地点；运行预算优先覆盖最多 5 个活跃 NPC。旧世界更多角色不删除，其余角色使用确定性日程延续，不逐个追加模型请求。

### 延后

真多 Agent、全天后台自治、Obsidian 文件同步、向量检索、自动无限 NPC、全地图模拟、战斗和经济系统、自由脚本化事件编辑器、任意多天自动挂机。

Obsidian 本期仅通过稳定 ID、来源引用和清楚的数据结构保持可导出性；不新建空适配层、服务或专用数据库。

## 5. 玩家界面与最小完整游玩路径

### 界面

游玩页顶部：世界名、第几天、早／中／晚、当前位置、精力简要状态，以及“世界管理”。

主体按顺序展示：当前场景、玩家实际观察到的在场者、最近剧情与对话、行动后果。输入区使用多行文本，支持中文输入法；组合输入期间 Enter 不误提交。可保留最多 3 个情境建议，例如“问她发生了什么”，不再展示 Action 枚举或系统分数。

世界列表和创建表单移至独立管理视图，避免持续占据阅读区。管理页分两层：普通管理展示世界资料、玩家已知人物／线索和存档操作；“作者／调试视图”显式进入，才显示完整日程、隐藏事实、事件内部状态和诊断。作者看到秘密不自动写入玩家知识。仅用 CSS 隐藏秘密内容不算过滤，游玩页 DOM 中不应包含它。

视觉沿用 `DESIGN.md` 的字体、色彩、正文优先和移动端约束。保留滚动位置、输入草稿、键盘焦点和最新反馈。持久化成功后才显示“已保存”。

### 贯穿验收的小故事

固定合成世界设定 3 人、5 地点，预置一个“文件去向不明”的可变事件，以及可调查的文件／便条对象。

1. 进入世界，后台准备当天日程，场景直接可读。
2. 输入“我去办公室找林雨”；抵达后按抵达时间确认她是否在场。
3. 输入“问她发生了什么”；她只能谈自己知道的争执，不能说出未知的真正拿走者。
4. 调查便条后，玩家获得新的可验证线索，后续建议随之变化。
5. 对在场 NPC 发出邀请；成功才改写后续日程，改期后原地点不能再次出现同一人。
6. 输入“睡到明天”；按规则推进事件，世界可能产生消息、关系变化或线索失效。
7. 玩家参与与连续忽略两条分支都能继续，结果不相同。
8. 刷新后保留当前场景、对话、时间、关系、线索与事件阶段。

这一故事是固定验证夹具。正式世界的事件候选可以由每日模型按状态生成，但不要求先建设通用世界生成器。

## 6. 行动、时间与提交规则

### 6.1 唯一执行链

输入／建议 → 意图解析 → 目标与前提校验 → `Action.execute()` 计算规则结果 → 生成必要文本 → 校验并保存整个回合 → 更新场景。

Daily Preview 是进入当日时独立的一次准备；`Settlement.settle()` 继续负责跨日，而且不调用模型。异步协调放在 `module4.js` 的一个小型 `submitTurn()`／`ensureDayReady()` 流程中。同步规则层仍可由现有 Node VM 测试直接调用。

模型只提供意图候选、受约束的文本或事件候选。时间、精力、存在的地点、NPC 在场、规则结果、日程改写资格以及最终写入由程序决定。禁止复制 Module3 的 `parseGameResponse()`／`applyParsedResult()` 协议。

仍保留当前日程改写限制：首期邀请只改变当天后续时段；跨天预约需要后续单独扩展，不能用一条自然语言承诺假装已经写入未来安排。

### 6.2 意图解析

先增强 `Action.parseFreeText()`：处理“我／我想”、已知地点名、人物名、简单代词、等待和睡眠。上下文中“她／他”只绑定当前会话或唯一可见对象；多人歧义返回一条澄清，不扣时间与精力。

本地不能确定且属于支持范围时，最多调用一次语义解析，输出固定字段：`type`、`targetNpcId`、`targetLocationId`、`targetObjectId`、`text`、必要的 `scheduleChange` 或 `waitUntil`。`energyCost`、成功与否、任意世界 patch 均不能由模型指定。所有 ID 必须再次对当前世界校验。

新增的解析状态为 `ready`、`needs_clarification`、`unsupported`；后两者不写成功行动日志、不推进世界，保留输入以便修改。输入“我拿到了所有秘密”不能直接成为 Fact。

复合句首期只支持 `move + seek`，先完整验证计划，再移动；抵达后的寻找是现场观察，不重复收费。没有遇见目标是合法结果，保留已经完成的移动。更长链条说明只能先做哪一步，不偷偷连续执行。

### 6.3 时间粒度：保持时段，增加刻度

建议默认每个早／中／晚时段包含 3 个行动刻度，新增 `clock.tick`，取值 0、1、2。刻度是玩法单位，不映射现实分钟。默认值集中在 Clock，可根据试玩调整，不在 UI 散落数值。

| 行为 | 默认耗时 | 精力 | 说明 |
| --- | --- | --- | --- |
| 看已知地图／状态／日志、重新阅读场景、输入澄清 | 0 | 0 | 无模型或使用已有文本 |
| 一轮实质对话、短移动、当前位置寻找 | 1 刻度 | 沿用 chat／move 的 5 | 连聊三轮最多推进一个时段，不直接过完一天 |
| 调查新对象、帮助、邀请／说服 | 1 刻度 | 调查／帮助类默认 10 | 真正的风险由规则决定 |
| 学习、探索、训练、高强度活动 | 2 刻度 | 沿用对应原成本 | 程序计算越界，不能跳漏事件 |
| 等到下一时段或指定的当日后续时段 | 剩余刻度 | 0 | 无 AI 结算；等待已到达时段为无操作 |
| 睡到明天 | 到次日早晨 | 不扣精力，跨日恢复 | 单次最多跨 1 日，不能无限循环或偷加日子 |
| 移动到当前位置 | 0 | 0 | 修正目前重复扣费、耗时的行为 |

日程仍按早／中／晚读取。非移动交互按行动开始时在场关系处理，结束时重新计算当前场景；移动按抵达时段判断相遇。跨晚间边界只经过 Settlement 一次。新一天 Preview 不属于 Settlement，也不在刷新时反复生成。

### 6.4 判定与有限对象交互

保留四档 deterministic Judgment。正常走路、普通问候、阅读已经公开的信息不判定；说服、遭拒风险、受保护物件、危险探索才判定。观察环境与风险探索不能因为都带“探索”二字就强制同一判定。

现有 Judgment 主要改变 NPC 关系／心情／临时状态，不等于已有物品、潜入或战斗系统。本期新增最小 `sceneObjects`：`id`、`name`、`locationId`、`holderId`、`state`、`affordances`、线索引用和必要的前提。仅支持检查／获得线索与受限拿取，不建设背包格子、重量、交易。

“拿文件”只有对象存在、位置可达、拿取权限和判定满足时才更新 holder／location；无效目标不扣费。判定失败可以产生已经定义的关系或事件后果；不能因“偷窃成功”套用通用关系 +2，或让一次失败凭空引发未定义死亡。

### 6.5 一回合一次落盘

- 对同一世界一次只接受一个进行中的回合；重复点击不能产生第二次规则执行。
- 模型请求基于 `worldId + revision + turnId` 快照；返回时发现世界改变、被删除或用户已切换，就不拿旧快照覆盖新状态。
- Action 在副本上计算；完成校验后，世界变化、Fact、事件推进、叙事条目和回合 ID 一起经 Store 保存。写入失败保持之前世界与输入草稿，不能展示虚假的成功状态。
- 机械行为不依赖模型：若润色失败，保存规则结果与本地短反馈，明确文本使用备用；重试文本不再执行行动。
- NPC 对话生成失败：不推进对话时间、不记为已交谈，不提交候选状态；玩家可重试。
- Preview 失败有明确 fallback 标记，同日不因 render、切页或刷新自动反复重试；若当天已有行动，恢复 AI 只能处理未来安排，不能重生成过去。
- `revision` 是过期检测，不是 localStorage 的原子事务。涉及多标签写入时，所有 Module4 写路径在原生 Web Locks 中先重读最新存储、再检查版本与保存；锁按整个存储 key，而非单个世界。环境不支持时按单写标签使用，不能宣传支持可靠多端并发。

这些约束落在现有 Store 和协调函数，不另建通用 World Engine、后台服务或消息队列。

## 7. 事实、角色认知与叙事文本

### 7.1 四类数据必须分开

| 数据 | 表达什么 | 进入世界真相的条件 |
| --- | --- | --- |
| Facts | 已经确认发生的事情 | 规则结果或已触发事件确认后提交 |
| Knowledge / Beliefs | 某人观察到、听说或怀疑的事情 | 有来源、观察者及明确传播动作；怀疑不等于客观事实 |
| Event plan | 未来可能发生的变化 | 条件满足并应用实际效果后，另产生 Fact |
| Narrative | 玩家读到的场景、对白和描述 | 本身无权改变规则状态 |

最小事实扩展：保留原 id、summary、actors、day、period，增加来源引用、观察位置、`knownTo` 或明确公开范围。参与者不自动等于全部知情者；未在场的人不能通过全局 Facts 获知秘密。

对错误认识，用按角色组织的知识条目记录 `claim`、`epistemicStatus`（观察／听说／推测）、来源 Action／Fact 与时间。不能为了记录“林雨怀疑陈雪”而生成客观事实“陈雪拿了文件”。无需本期建设信念推理引擎。

### 7.2 上下文先过滤再请求

NPC 交互输入只含自身稳定资料、当前状态、可知线索、与当前对象有关的历史和现场信息。玩家场景输入只含玩家可见事实与可观察动作。

禁止把全部秘密放进提示词，再写一句“你不知道这些”。也禁止把完整角色卡里的 creator notes、system prompt、隐藏设定不加分级地注入所有 NPC。

对本人知道但不该公开的秘密，程序先判断是否允许在本次对话披露；普通对白生成仅接收可披露内容和“不愿谈此事”等抽象态度，不附上秘密正文。世界预演可用更广的内部事实，但它的原始输出不直接展示给玩家。

玩家编造的陈述按“玩家说过 X”或他人的待证实听闻记录，不能倒写 X 为真。新文本不能擅自创造跨角色共享知识。

### 7.3 NPC 差异化与真实对话

实现现有 `ai/interaction.js`，首期一轮最多指定一个主要说话 NPC；其他在场者以可观察简短反应出现。不同人物分别组装输入，群像轮流对话后续再加。

源角色资料生成一次经过长度限制的稳定角色摘要；不靠每日 Preview 重写人格。现有 `npc.goals` 保留持续目标，新增／区分当天短目标，不能像当前 applyPreview 那样每天完全覆盖长期方向。结构化 mood 用固定枚举，玩家展示可用中文描述，避免中文心情值进入当前英文评分表后全部按 0 处理。

首期摘要从明确公开的角色字段确定性抽取；未分级的长卡内容留在作者资料中，由世界管理显式选定公开设定。不要默认另开一次模型“读完整卡并总结”的请求，更不能把长度裁剪误当秘密过滤。新增秘密通过有知情范围的知识／事实记录表达。

模型输出至少区分正文、允许引用的事实／线索 ID 和候选知识披露。新增持久状态必须匹配 Action、对象 affordance 或明确事件规则；不接受任意 JSON patch。请求和响应做结构、ID、长度校验，渲染内容转义，原始提示词与响应不进入诊断日志。

应如实承认：结构验证能保证状态不会被任意改写，不能数学上证明每句自由文本完全无幻觉。用少量语义验收检查角色差异和泄密；硬结果使用程序回执展示。不得用模型自评作为唯一验收依据。

## 8. 轻量 Preview 与世界推进

### 8.1 Preview 的职责

一天正常最多一次模型预演，输出重要 NPC 的三段短计划、当天短目标、少量候选事件或既有事件下一步建议。场景正文和 NPC 对话不在这里生成。

同日只生成一次有效安排；不同 NPC 数量不直接变成多个请求。重要角色优先级由在场／相关事件／近期交互决定，其余角色用已保存计划与本地默认值延续。

保留对稀疏 JSON 的兼容：缺活动可用短目标，缺地点优先用已知当前／常驻地点，再用合法默认地点；缺字段标为“本地补齐”。未知地点 ID 从新结果中拒绝或映射到明确已有别名，不能进入 `Location.normalizeWorld()` 自动造地点。旧存档的历史地点迁移行为单独保留。

零 NPC 世界和 API 不可用世界仍可移动、等待、睡眠；不得把空世界的 completed 状态或 fallback 当作模型验收成功。

### 8.2 有限事件记录

新增一个小型 `core/events.js`，不构造可执行脚本／DSL。事件记录至少包含：

- `id`、稳定去重标识、主题、参与者和关联地点／物件；
- 当前 `stage` 与 `status`（active、resolved、expired）；
- 已知触发类型、最早触发时段、期限、冷却与最近推进标记；
- 允许的分支／下一步候选、受限效果和可见性；
- 来源 Fact／Action／Preview、已实际应用的 transition ID。

可用触发首期只支持：到达时段、进入地点、取得指定线索、完成指定行动、判定结果、到期。模型不能输出待 eval 的条件代码。程序检验人物／地点／对象引用以及前提，未知触发或无依据的效果不入队。

效果白名单首期只含：更新事件阶段／期限、变更已存在物件的 state／holder／location、应用已定义的 NPC 心情和有限关系变化、登记有来源的线索／知识，以及产生上述已生效变化的事实。NPC 彼此关系使用 `world.npcRelations` 中仅涉及事件的有向人物对记录，不覆盖各 NPC 对玩家的 `relation`，不模拟完整社会网络。

候选不作为活跃事件直接生效；校验通过后才加入世界，真正触发时再应用一次效果与 Facts。持续事件放 `world.events`，不得只存在会被跨日清空的 `currentDay.events`。

### 8.3 推进节奏

- 开局若无未解决事件，可给一个与世界和人物目标有关的轻量事件候选。
- 每天新增候选最多 1 个；同时活跃事件最多 3 个，优先推进旧事件。
- 单事件同一时段最多推进一次，同一回合最多处理 3 个事件转换；去重依据 transition ID，不依赖展示文本。
- 等待／睡眠跨多个边界而达到处理上限时，停在已处理的时间点，保留后续待处理事件，并提示继续等待；不能先把时间跳完再丢掉积压事件，也不能在尚未完成跨日时恢复睡眠精力。
- 每个关键事件保留至少两种可能出口，例如玩家参与后解决、无人介入后到期或转向；不把整条固定主线隐藏到后台再强推。
- 人物关系不只会恶化；忽略也允许缓和、别人解决、错过机会。事件可以结束，不能永久堆积。
- 不以“世界必须活着”为理由每天制造危机；允许平静一天。
- 到关键选择节点可以停止等待并提示玩家；纯后台轻微变化继续按规则计算，不逐条调用模型。

所有转换在实际行动或时间边界触发。页面挂着、查看管理、刷新不调用事件推进；已经完成的睡眠不能因为请求重试再过一天。

### 8.4 日结兼容

V1.5 日结不再无条件把预演计划转成 Facts。只有事件引擎确认已发生的转换能够写事实；已有旧 Facts 不反向删除。

日结保存事件状态、短日志、NPC 持续目标与长期关系，清理当日临时状态。次日 Preview 根据事实和活跃事件生成未来计划，不改写已发生历史。

## 9. 调用与上下文预算

以下是建议实施默认值，不是当前已测得的性能。上线前用固定场景校准。

| 场景 | 正常模型调用 | 失败上限与处理 |
| --- | --- | --- |
| 看状态／旧场景、等待、睡眠、相遇、规则判定 | 0 | 0；跨入新日的 Preview 单独计数 |
| 明确移动／调查／规则动作 | 0；需要新场景润色时可为 1 | 润色失败用本地回执，不重复动作 |
| 已识别 NPC 对话 | 1 | 自动不重试；允许玩家主动重试失败对话 |
| 需模型解析的自由表达，再生成回复 | 最多 2 | 总计不超过 2；不叠加第三个裁判请求 |
| 新一天 Preview | 1 | 最多额外重试 1 次，随后 fallback |
| 单次输入同时跨日 | 回合与 Preview 分列 | 极端合计上限 4；预算须显示归因，不宣称仍是 0～1 |

复杂冲突首期也使用现有规则裁判，不引入独立“裁判模型 + NPC 模型 + 叙事模型”串行调用。

上下文取数优先级：本次行动与规则结果 → 当前场景 → 相关 NPC 稳定摘要 → 最近最多 6 轮相关对话 → 最多 12 条已过滤事实／线索 → 活跃事件摘要。历史搜索先按实体 ID、标签和最近时间取少量命中，不上向量库。选择是确定性步骤，不额外调用检索 Agent。

建议初始序列化消息上限：普通回合 12,000 字符，Preview 16,000 字符；单角色稳定摘要约 800 字符。超限优先删无关历史、旧日程和非当前角色，不能删除执行约束或知情过滤规则。字符上限是可验证的输入约束，不等于真实 Token 数。

现有 `callLLM` 丢弃 usage，只返回正文；诊断首期记录调用用途、次数、字符数、耗时、结果码和本地补齐状态。报告“估算”与“实际 usage”分开。输出长度提示也不是硬 token 限流；沿用共享 Settings 的输出上限，不为了预算修改全局配置或新建 Module4 API 页面。

若后续确需逐调用硬上限或 usage，在单独的公共 transport 兼容改动中实现，并验证 Module3；它不是首轮玩法闭环的前置条件。

## 10. 存档演进与兼容

首期仍使用原 Module4 存储命名空间。不要从旧目录／其它 origin 偷拷 localStorage，也不要修改 Master、角色卡原件或 Module3 Adventure。

建议按世界逐个升级：新增世界使用 `schemaVersion: 2` 和 V1.5 规则；旧世界默认保留原玩法，由用户在管理页选择“复制为 V1.5 世界”建立新 ID 的升级副本，原世界不变。第一轮验收全部在合成测试世界进行。

兼容规则：

- 迁移只补 `clock.tick=0`、`revision`、叙事条目、事件和知识的默认结构；保留未知旧字段、原 Facts、来源快照与历史。
- 旧世界的旧行动日志不重新解释为新动作，不回算时间或精力。
- 旧 Facts 保留历史含义；缺认知来源标为 legacy，NPC 不默认全知，后续通过实际观察／披露建立知识。
- 未分类的旧当天 events 在升级副本里标为 legacy，不能自动充当新事件种子并触发效果。
- 同日已有有效 Preview 优先保留；只对未来缺项补齐，不能升级后立即推翻原有安排。
- 原存储外层 version 与世界 schemaVersion 分开管理；旧世界的 Clock／Settlement 使用旧规则，新世界根据明确版本走新分支，避免半迁移。
- 保存前检查序列化体积；接近容量时提供完整世界导出和说明，不默默删除 Facts／对话。仍保留旧世界在同一个 key 时，复制因容量不足应失败并保持原状态。

叙事记录建议复用每个 turnId，只保存一份正文并引用 actionId／factIds，不在多个数组中复制全文。初期近期上下文有上限，长期存档不因此自动裁掉；达到容量后需要导出／归档，是明确的单机容量边界。

原始 JSON 损坏时应保留原始值并进入恢复提示，不能无声变空后让下一次保存覆盖唯一存档。导出包含游玩数据但不含共享 API 配置；导入或复制前完整校验，失败不影响现有世界。

依赖：S3、S4。

- 调整 `ai/preview.js`、`ai/prompts.js`：精简 sourceSnapshot，限制活跃角色，补合法日程缺项。
- `module4.js` 进入新日自动 `ensureDayReady()`，保存一次后才启用依赖日程的行动；无 NPC 时直接可玩。
- `core/location.js` 区分迁移与新模型 ID 校验；`Schedule.getEffectiveSlot()` 仍是唯一日程读取入口。
- fallback 的手动恢复只作用未来，已发生行动与被邀请改期的时段保持一致。

通过条件：不用点击“生成预演”就可开始；刷新不多请求；缺字段仍可遇见合法地点上的 NPC；未知地点不会凭空出现；同日重试不覆盖改期。

### S6：跨天事件与有限世界变化（中到大）

依赖：S2、S3、S5。

- 新增 `core/events.js`；World、migrations 增加持久事件记录。
- Preview 只提出有限候选；Action／时段边界确认转换；Facts 只记录实际发生的变化。
- 仅为参与事件的人物对建立有限 `npcRelations`；分别验证它与 NPC 对玩家关系互不覆盖。
- Settlement 保留持续事件，玩家日结视图仅显示可知变化。
- 用固定事件证明“参与”和“忽略”至少产生两种可解释结果，再允许模型提出新候选。

通过条件：计划不会直接变事实；同一转换不重复；关页面不推进；睡眠推动到期事件；刷新后阶段保持；事件能解决／过期；活跃数、每日新增数和调用次数均有界。

### S7：连续游玩与正式包验收（中）

依赖：S1–S6。

- 固定世界跑完至少 3 个完整游戏日，再用无模型的可控夹具走 7 日，验证重复推进、累计成本、认知传播、事件结束和历史大小。
- 复用已有浏览器做关键用户路径验证；现有 Node 测试覆盖纯规则。无需为本阶段引入新框架。
- 按现有 `sync-narraverse-assets.mjs` 与正式构建／启动链同步、构建和检查实际 executable URL，不能用静态页代替正式验收。
- 检查 Module1–4 入口、共享 Settings、Module3 切回、滚动、资源和刷新；用户数据不用于破坏性验收。
- 更新代码指南、必要的当前说明和协作日志；提交仅包含精确任务文件。若之后需要 PR，再按实施授权执行，不夹带当前翻译改动。

通过条件：下面验收矩阵全部达到，真实模型结果与 mock／fallback 结果分别记录。任何存档覆盖、秘密泄漏、计划变事实或重复耗时问题阻止发布。

### 可交付节点与工作量判断

- S1 是体验样张，可提前检查阅读布局，但不是可玩版。
- S2–S5 完成后是可游玩的交互闭环，暂不宣称世界具有完整跨天事件推进。
- S6–S7 完成才称为本方案定义的 V1.5。

建议拆成 5–7 个小批次提交，规则／存储改动尽量不要和大段 UI 变更混成一个评审批次。复杂度最高的是 S2、S4、S6。它们分别涉及时间与存档、真实模型、事件因果，不能按“几个提示词加一个输入框”估时。先完成 S0–S2 后再根据实际差异给排期，不承诺未经试作的固定天数。
