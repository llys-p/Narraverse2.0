# 第二版《翻译功能五项问题修复方案》可行性复审

## 总体结论

我把你上传的第二版方案重新对照了当前 `Narraverse2.0` 的真实 `main`、Python 翻译任务实现、Master Library / material import / Lore 更新逻辑、LibraryView、TranslationQueueControl、API client 和现有路由。

**结论是：第二版的整体方向是对的，但目前仍不建议直接进入编码。**

更准确地说，它已经把“五项问题分别怎么处理”的路线搭出来了，但第一轮审阅里最重要的几个问题，**有一部分在第二版里仍然没有真正落到可执行设计上**。当前可以这样分级：

| 问题 | 第二版状态 | 结论 |
|---|---|---|
| 翻译偶发英文回显 / 重试 | 方向正确，但质量判定仍有漏洞 | **BLOCK** |
| 缓存升级 / 坏任务重新进入翻译 | 仍未解决任务身份与已应用坏译文 | **BLOCK** |
| Master → 当前冒险同步 | 边界仍偏大，且有编译、误同步、状态一致性问题 | **BLOCK** |
| 润色 Proposal 等待 | 基本可行，但轮询关联方式还能明显简化 | **可实施前小修** |
| 清理失败队列 / 手动刷新 | 基本可行 | **小修后可实施** |

尤其值得注意的是：当前 `main` 中翻译任务 ID 的摘要仍然只包含 `TRANSLATION_CACHE_VERSION`，而缓存 key 才同时包含 cache/prompt/validator 三种版本；Master Library 的 `masterHashString` 仍然是 `book` 包内部的未导出函数；现有 Master 实例本身已经保存了 `MasterItemID`、`LoadedRevision`、目标 Lore ID 和 adventure workspace 等信息。这些真实代码结构都支持第一轮审阅提出的结论：**同步应该做成 `book.Service` 内部的资产级操作，而不是 Handler 自己重新推导 import transaction。** fileciteturn3file0 fileciteturn5file0 fileciteturn6file0

所以我建议不要推翻第二版，而是做一次很有限的 **“第三版设计收口”**。真正需要修改的是几个接口和不变量，而不是重新设计五项功能。

## 翻译质量与缓存：第二版最大的剩余风险

### 翻译重试不应该再采用“第二次中文更多就选第二次”

这是第二版目前最明显的逻辑问题。

方案当前 `_translate_chunk()` 的思路大致是：

```python
第一次翻译
↓
统计英文 / 中文字符
↓
觉得英文太多
↓
第二次强化提示重试
↓
如果第二次中文字符比第一次多
    采用第二次
↓
最终只检查中文字符不是 0
```

问题在于，**“第二次比第一次中文更多”和“第二次已经合格”完全不是同一件事。** 上传方案中的第二次接受条件仍然允许类似：

```text
第一次：
The character walks into the room.

第二次：
角色 walks into the room，然后 sees Alice.
```

第二次当然“中文更多了”，但它仍然是明显失败的中英混杂译文。第二版当前的最终检查如果只要求存在中文，就仍可能把它接受。fileciteturn0file0

这里最好不要继续往 `_translate_chunk()` 里增加第三、第四个统计条件，而是把设计简化成：

```text
candidate #1
    ↓
统一质量校验
    ├─ PASS → 返回
    └─ FAIL（可重试类型）
              ↓
          candidate #2
              ↓
          同一个质量校验
              ├─ PASS → 返回
              └─ FAIL → 整个翻译失败
```

也就是说：

> **不存在“两个坏结果中挑一个比较好的”这条分支。**

只有：

> 合格 / 不合格。

当前 Python 实现本来就已经让缓存命中的译文走 `_validate_output()`，新模型输出也会进入验证，因此把“明显英文回显 / 中英混杂”并入 `_validate_output()`，会比在 `_translate_chunk()` 里额外做一套独立判断更一致。这样旧缓存、新缓存、首次生成、重试生成使用的是同一套质量合同。fileciteturn3file0 fileciteturn12file0

### 占位符问题还可以再修严一点

你的第一轮审阅已经正确指出：

```text
__NV_PROTECTED_0000__
__NV_EXISTING_ZH_0000__
```

会给 Latin 字符统计制造大量噪音。

第二版目前只在输入 probe 上移除了 `__NV_*__` placeholder，而输出统计仍可能受到 placeholder 影响，因此还没有彻底解决。fileciteturn0file0

我建议比第一轮再推进一步：

**质量统计时不仅忽略 placeholder 本身，还应该忽略被保护内容本身。**

原因是现有翻译管线会保护 URL、代码、专名等内容，并在后续恢复；而缓存保存的是恢复后的译文。如果质量判断最后统一进入 `_validate_output()`，例如一段正常译文：

```text
访问 https://example.com/api/v1/users，然后继续。
```

里面天然就有大量 Latin 字符。这不应该被算成“模型英文回显”。现有 Python 管线已经持有受保护 token 与原始值之间的映射，因此可以在质量分析视图里排除这些受保护片段，而不改变真正返回给用户的文本。fileciteturn3file0

建议形成一个概念上的：

```python
quality_view(text, protected_values)
```

它只供质量判断使用：

```text
原文 / 译文
↓
移除 __NV_*__ placeholder
↓
移除已知 protected originals
↓
再统计真正应该翻译的 Latin / CJK
```

不要直接为了统计而改最终译文。

### 英文回显规则也不要简单写成“Latin 比例 > X”

建议质量规则至少区分：

**确定失败：**

```text
需要翻译的原文明显含英文
+
译文无中文
```

以及：

```text
去掉 protected 内容后
译文仍保留大量连续英文自然语言
```

但不要因为：

```text
Alice
OpenAI
HP
NPC
JSON
API
```

这种合理保留词就判翻译失败。

也就是说，要判断的是：

> **自然语言英文回显**

而不是：

> 出现英文字母。

这是对第二版翻译检查最值得做的一次优化。

## 任务版本与坏译文修复：不能只升级缓存

这一点第二版目前依旧不足，而且它会造成一种非常隐蔽的“我明明修了 validator，怎么旧数据还是坏的”的情况。

当前主线代码里：

```text
PROMPT_VERSION = 7
VALIDATOR_VERSION = 7
TRANSLATION_CACHE_VERSION = 10
```

而缓存 key 会包含多个版本，但翻译任务 ID 的摘要目前只组合了：

```text
source_file
model
TRANSLATION_CACHE_VERSION
```

并没有把 `PROMPT_VERSION` 和 `VALIDATOR_VERSION` 纳入任务身份。fileciteturn3file0

第二版准备把：

```text
PROMPT_VERSION → 8
VALIDATOR_VERSION → 8
```

但仍保留：

```text
TRANSLATION_CACHE_VERSION = 10
```

那么结果是：

```text
模型缓存
→ 因 prompt/validator 版本变化失效 ✅

翻译 job identity
→ 没变化 ❌
```

也就是说这只能解决：

> 下一次真正进入 translator 时不读取旧 cache。

它不能保证：

> 那些已经存在于任务系统里的任务会重新进入 translator。

更不能修：

> 已经被 apply 进 Master、现在处于 active 状态的坏译文。

当前已有 `retry_translation_job` 也不是通用的数据迁移工具。它针对失败、冲突、取消等状态重新调度现有任务，并不能自动发现所有“过去已经成功应用、但其实中英混杂”的 active 翻译。删除接口同样是失败队列的软删除，并保留审计记录，不承担 active Master 数据回滚职责。fileciteturn3file0 fileciteturn12file0

### 推荐把版本问题一次解决

这次最小可以：

```text
TRANSLATION_CACHE_VERSION = 11
PROMPT_VERSION = 8
VALIDATOR_VERSION = 8
```

但长期更稳的方式，是让 task digest 本身明确包括：

```text
source identity
model
translation cache version
prompt version
validator version
```

这样以后再升级 Prompt：

```text
8 → 9
```

不需要靠“顺便记得再把 cache version 改 12”维持任务身份正确。

### 还必须有“历史坏译文重新进入系统”的入口

第二版应明确区分三个东西：

```text
Cache
    模型结果缓存

Translation Job
    一次翻译任务

Applied Master Translation
    已经成为当前 Master 数据的译文
```

这三层不是一回事。

因此建议第二版增加一条非常明确的迁移策略：

> 对经过新 validator 判定为不合格的已应用译文字段，允许创建一个使用新版本身份的重新翻译任务，而不是假设 cache invalidation 会修复它。

这不一定需要做一个复杂的“全库迁移按钮”。

可以是一次性 bounded repair：

```text
扫描候选翻译字段
↓
使用 validator v8 做质量检查
↓
仅列出不合格字段
↓
为这些字段建立新的 translation job
↓
正常走 Proposal / apply 流程
```

这样不会无条件重新翻译所有已经正常的中文。

### 建议增加两个版本测试

除了你已经列出的测试，我会再补：

```text
PROMPT_VERSION 改变
→ task identity 必须改变
```

以及：

```text
VALIDATOR_VERSION 改变
→ 旧 cache 不能直接恢复成有效结果
```

这两个测试能防止以后版本字段重新脱钩。

## Master 同步：方向正确，但接口必须降到“单资产”

问题三是第二版目前最大的后端风险。

### `ReprojectMasterImport(importID)` 仍然是错误抽象层级

你第一轮审阅提出：

```go
ReprojectMasterAsset(masterItemID string)
```

我认为这是正确的，而且经过当前代码结构复核后，比第一轮时还更确定。

现在 Master 实例数据本身已经记录了：

- `MasterItemID`
- `LoadedRevision`
- `TargetLoreIDs`
- `NestedEntryLoreIDs`
- adventure workspace 信息

现有 `PrepareAssetInstantiation()` 也已经在 `book.Service` 内部完成了“当前 Master Asset + 当前 Adventure”的实例匹配，而不是要求 Handler 自己算 manifest hash。fileciteturn5file0

因此正确边界应该是：

```go
Handler
    ↓ masterItemID
BookService.ReprojectMasterAsset(masterItemID)
    ↓
Service 自己定位 current adventure instance
    ↓
Service 自己读取 Master active revision
    ↓
Service 自己完成 projection
```

Handler 最好只做：

```text
解析请求
↓
调用 BookService
↓
转换错误到 HTTP response
```

这也符合当前 handlers 已有的 Service 调用方式。fileciteturn6file0

### `masterHashString` 不是“风格不好”，而是会直接编译失败

第二版如果仍计划让 handlers 里直接调用：

```go
masterHashString(...)
```

则不能实现，因为它是 `book` 包未导出的函数。

Go 中小写标识符是包私有的，`handlers` 不能跨包调用。当前源码也确实将它作为 `book` 内部 helper 使用。fileciteturn5file0

不要为了让 Handler 能用它而把：

```go
masterHashString
```

改成：

```go
MasterHashString
```

这只是把错误的架构边界公开化。

资产同步根本不应该要求 Handler 知道 hash 的存在。

### 同步整个 import transaction 会造成真实误同步

第二版的：

```go
ReprojectMasterImport(importID)
```

如果遍历：

```go
transaction.ItemIDs
```

就把“导入事务”和“用户点击的资产”混成一个更新边界。

如果一次 import：

```text
Import A
├─ 角色 Alice
├─ 角色 Bob
├─ 世界观 Lore
└─ 地点 Tavern
```

用户在 Alice 上点：

> 同步到冒险

预期是：

```text
Alice
```

更新。

不是：

```text
Alice
Bob
Lore
Tavern
```

一起重新投影。

所以这里应该坚持：

```go
ReprojectMasterAsset(masterItemID)
```

而不是给 `ReprojectMasterImport()` 打更多补丁。

### 名称 `-2` 的问题第二版还没有真正解决

当前 `buildMasterRuntimeOperations()` 会先根据全部 existing Lore entries 初始化名称分配器，再对投影条目 claim name。fileciteturn4file0

普通“新导入”时这是对的：

```text
已有 Alice
新导入 Alice
→ Alice-2
```

但同步已有 Alice 时：

```text
Existing:
Alice ← 其实就是自己

然后同步 Alice
↓
allocator 看见 Alice 已被占用
↓
Alice-2
```

第二版如果只是**生成 operations 后**再检查目标名是否冲突，已经太晚：

```text
Alice
↓
build operation
↓
被改为 Alice-2
↓
再问 “Alice-2 是否冲突？”
↓
没有
↓
错误名称被保留
```

因此修复点必须在投影操作生成之前。

更合理的是：

```text
existing entries
-
当前 MasterInstanceRef 的 target IDs
=
name allocator 的 existing set
```

然后再运行 projector。

这样它会看见：

```text
其它资产的 Alice → 冲突
自己原来的 Alice → 不冲突
```

这才是正确语义。

### “目标条目丢了就 continue”绝对不能保留

第二版目前：

```go
target missing:
    continue
...
LoadedRevision = active revision
```

这是数据状态上最危险的部分之一。

因为最后 UI 会得到：

```text
LoadedRevision == Master ActiveRevision
```

从而显示：

> 已同步

但实际上可能：

```text
3 个目标条目
2 个更新
1 个根本不存在
```

这属于假成功。

正确不变量应该写死：

> **预期 target set 不完整，整次 asset reproject 失败，LoadedRevision 不变化。**

同理：

```text
成功同步内容
+
更新 LoadedRevision 失败
```

也不能留下一个半成功状态。

当前 material import 原始流程本身已有 snapshot / rollback 一类的错误恢复设计，所以资产重投影最好继续遵守这种一致性思路，而不是把 Lore update 和 manifest revision update 当成完全无关的两次写入。fileciteturn4file0

### 我会再补一个第二版没有强调够的问题：同步最好具备原子性

理想结果只有两个：

```text
A.
Lore 更新成功
LoadedRevision 更新成功
→ synced
```

或者：

```text
B.
任意步骤失败
Lore 恢复
LoadedRevision 不变
→ failed
```

最差的情况是：

```text
Lore 已经变成新版
LoadedRevision 仍旧版
```

用户下一次又会看到“需要同步”，再次同步一次。

反方向：

```text
LoadedRevision 已新版
Lore 实际未全部更新
```

更危险，因为 UI 会认为同步成功。

因此建议 `ReprojectMasterAsset()` 自己拥有这一整个写操作生命周期，而不是 Service 返回 operations、Handler 再分别写东西。

### “稀疏 Update”这四个字需要重新定义

第一轮方案提出：

> 为本地 Enabled、图片、加载模式等字段生成稀疏 update。

方向是对的，但实际 `LoreItemInput` 并不是一个完全意义上的 PATCH DTO。

现有 `Lore.Update` 对多个字符串字段采用输入值作为新状态，而不是所有空字符串都表示“保持旧值”；`Enabled` 因为是 pointer，有明确“不提供则保持”的能力，图片还有自己的保留逻辑。fileciteturn7file0

因此不要写：

```go
LoreItemInput{
    Content: newContent,
    // 其它留空，以为代表 preserve
}
```

这很容易把：

```text
Name
Tags
LoadMode
BriefDescription
...
```

无意清掉。

更稳的是定义字段所有权：

```text
当前 existing target
        ↓
复制当前本地状态
        ↓
只 overlay Master-authoritative 字段
        ↓
Update
```

比如：

**Master-authoritative：**

```text
翻译后的正文
由 Master 定义的语义字段
必要的来源 revision
```

**Adventure-local authoritative：**

```text
Enabled
本地图片选择
本地加载模式
以及产品明确允许冒险自行调整的字段
```

然后用现有 revision/concurrency 字段做乐观并发保护，避免用户正好在同步期间编辑 Lore 时被静默覆盖。fileciteturn7file0

这比单纯“传空字段”安全很多。

### Opening presets 必须在方案中明确，不应该留到实现者猜

当前 Master 初始投影并不只有最简单的 Lore operation；material-import 流程还存在角色卡相关的后续运行时处理。fileciteturn4file0

因此第二版至少必须明确：

> Character opening presets 到底是不是 Master → Adventure 同步契约的一部分？

有两种都可以：

**方案 A：属于**

那么角色 Master 更新后，相关 opening preset 也需要同步，并明确本地字段如何保留。

**方案 B：不属于**

那么同步按钮只同步 runtime Lore projection，opening preset 是实例化时快照，后续本地拥有。

但不能当前什么都不写，最后 UI 又笼统显示：

> 资产已同步。

我的倾向是 **P0 先采取 B**，除非现在确实存在用户修改 Master 角色卡后必须同步 opening preset 的明确需求。这样能够把这次五项修复保持 bounded。

## 前端 Proposal 与失败队列：不需要做重

### 润色轮询已经可以做，但第二版的状态提升过头了

当前 `LibraryView` 的真实行为只是：

```text
点击润色
↓
startMasterAgent(mode="polish")
↓
告诉用户任务已启动
```

并不会等待 Proposal 真正产生。fileciteturn8file0

所以问题四的基本判断是正确的：

> `onPolish()` 不应该在 agent 启动成功后立刻算完成，而应该等真正的 Proposal 到达最终状态。

但第二版如果为了一个按钮 loading，把：

```text
polishingPaths
```

提升到 LibraryView，再一路经：

```text
renderTranslationSection
↓
TranslationFieldBlock
↓
TranslationFieldRow
```

传下去，我认为复杂度没有收益。

更简单的是：

```text
TranslationFieldRow
    owns:
        polishing
        polishError
```

然后：

```ts
await onPolish(...)
```

直到轮询结束后 Promise 才 resolve/reject。

于是 Row 自己天然可以：

```ts
setPolishing(true)
try {
  await onPolish(...)
} finally {
  setPolishing(false)
}
```

不需要整个页面知道哪个字段正在 polish。

### Proposal 匹配不要主要依赖浏览器时间戳

第二版目前类似：

```text
field_path 相同
kind == polish
updated_at >= started - 1000ms
```

这存在几个边界问题：

- 客户端和服务端时间有偏差；
- 同一字段短时间连续润色；
- 旧 Proposal 恰好刚更新；
- 浏览器恢复 / 页面切换。

API 类型本身已经有稳定的 `proposal_id`，Proposal 还带 `agent_run_id`；而 `startMasterAgent()` 返回的是一个 `task_id`。目前仅从接口类型不能可靠证明 `agent_run_id === task_id`，因此不能直接把它作为契约，但这值得后端确认。fileciteturn11file0

在不改变后端协议的前提下，我推荐：

```text
开始前
existingProposalIDs = Set(...)

启动 polish
↓
poll
↓
寻找：
    proposal_id 不在 existingProposalIDs
    field_path == 当前字段
    kind == polish
```

然后：

```text
candidate_ready / validated
→ success

conflict / rejected
→ 立即失败

其它 processing state
→ 继续 poll

timeout
→ timeout
```

这样比时间戳可靠得多。

如果以后确认：

```text
start task_id ↔ proposal.agent_run_id
```

有正式一一关联，那再升级成 run-ID correlation 会更稳。

### 还缺一个生命周期清理

第二版需要明确：

当：

- 组件卸载；
- 用户切换资产；
- LibraryView 关闭；
- 新一轮 polish 覆盖上一轮；

旧 polling timer 必须终止。

否则会出现：

```text
用户已经打开 Bob
↓
Alice 的 polish polling 回来
↓
刷新 Bob 页面 / 弹 Alice 消息
```

所以至少要有：

```text
cancelled/ref
```

或统一 poll disposer。

### “当前冒险能否同步”最好由后端给事实

你列出的测试：

> 资产只存在于其它冒险时，当前冒险不能误显示为可同步。

非常重要。

如果第二版 UI 仍简单判断：

```ts
activeItem.usages.length > 0
```

那么“该 Master asset 在任何 Adventure 使用过”和“当前 Adventure 有对应实例”是两回事。

最理想的是后端 Detail API 在当前 workspace 上下文直接返回：

```json
{
  "adventure_sync": {
    "instantiated": true,
    "loaded_revision": "...",
    "active_revision": "...",
    "stale": true
  }
}
```

这样 UI 不需要自己重新解释 `usages`。

但如果不想扩大本轮 API schema，最小方案也应该由：

```go
ReprojectMasterAsset(masterItemID)
```

作为最终权威：

```text
当前冒险无实例
→ 明确返回 not_instantiated
```

UI 即便偶尔多显示了按钮，也绝不能发生跨冒险同步。

### 清理失败任务只需要小修，不需要新后端

当前 Translation Queue 已经有约 **1.2 秒自动刷新**，因此新增“刷新”按钮的意义确实只是：

> 用户刚做完操作，现在立刻刷新。

不是修复数据同步机制。fileciteturn9file0

这个按钮可以保留，因为用户体验合理。

真正要改的是：

```ts
const [clearing, setClearing] = useState(false)
```

和：

```text
已清理 {done}/{total}
```

之间不一致。

推荐：

```ts
type ClearProgress = {
  running: boolean
  done: number
  total: number
  failed: number
}
```

然后为了避免一下子对本地服务打很多 DELETE，我更倾向**继续串行删除**，但逐项捕获：

```text
for each job
    try delete
    catch:
        failed += 1
    finally:
        done += 1
```

最终：

```text
全部成功：
已清理 12/12

部分失败：
已处理 12 项，成功 10，失败 2
```

而不是第一个失败就中断余下 11 个。

现有删除语义本身是软删除：从可见 Translation Queue 中移除，但审计文件仍保留，因此不需要为“清理失败项”增加另一套后端批量删除机制。fileciteturn3file0

## 建议的第三版最小设计

我建议不要再写一份几十页的“第三版重新设计”。只需要在现有第二版补上以下合同，然后就可以进入实施审批。

### 翻译部分

将核心逻辑收敛成：

```text
Translator
│
├─ 调模型 candidate #1
│
├─ restore protected content
│
├─ unified _validate_output()
│      ├─ structural validation
│      ├─ protected-content validation
│      ├─ echo validation
│      └─ translation-quality validation
│

       ↓
   完全相同的 validator
       ├─ PASS → cache + return
       └─ FAIL → job failed
```

明确：

质量统计排除：

```text
已知 protected originals
```

版本改为至少：

```text

```

并把三者纳入未来 task digest。

同时增加：

```text
已应用坏译文 → 一次性识别 → 新任务重翻
```

的明确 repair path。

### Master 同步部分

接口收敛成：


Handler：


Service：

```text
↓

↓

↓

↓
apply
↓
更新“这一个 MasterInstanceRef”的 LoadedRevision
```

任一失败：

```text

```

最好进一步做到：

```text

```

失败时一致回滚。


### 字段所有权明确写入方案

建议方案里直接放一张小表，而不是让实现者临场猜：

你第一轮列出的测试基本都应该保留。我在源码复核之后，建议最终测试集至少覆盖下面这些“真正会阻止合并”的场景。

**翻译测试：**

```text
→ PASS

第一次混杂、第二次仍混杂
→ FAIL
```

```text
→ B/C hash/state 完全不变

→ B 完全不变

当前 Adventure 未实例化

名称 Alice

→ 不出现 Alice-2

→ LoadedRevision 不变

本地 Enabled
→ 保持

→ 保持

→ 保持
```

### 最终实施判断

我的最终评级是：

> **第二版方案：设计方向 PASS，直接实施 BLOCK。**
>
> 不需要重新设计五项功能，但需要做一次小范围的“第三版设计收口”。

真正的阻断点只有三组：

**翻译质量合同必须统一。**
不要“第二次中文更多就接受”；所有 candidate 必须经过同一个 validator，protected 内容不参与英文回显统计。

**版本升级必须同时覆盖 cache、job identity 和 already-applied data。**
仅升级 Prompt / Validator 版本不能自动修复历史坏任务和已应用坏译文。当前任务摘要仍只使用 `TRANSLATION_CACHE_VERSION`，这在源码中可以直接确认。fileciteturn3file0

**Master 同步必须从 import 级改成 asset + current-adventure-instance 级。**
由 `book.Service` 自己定位实例、投影和提交 revision；Handler 不解析 manifest/hash；target 缺失即失败；名称分配前排除自己的目标；本地字段按所有权显式保留；同步内容和 `LoadedRevision` 需要具备一致性。当前 Master manifest 和实例数据结构已经提供了实现这种边界所需的信息。fileciteturn5file0turn4file0

问题四和问题五则不用再扩大：

> **Proposal：换成“新 Proposal ID + 行内 loading + 生命周期清理”。**
>
> **Queue：换成进度对象 + 逐项捕获失败。**

做到这些以后，我会把方案评级提升为：

> **IMPLEMENTATION READY**

而且我不建议再为这五项功能增加新的后端批量接口、新状态管理层或新翻译框架。现在真正需要的是把**质量判定、数据所有权、同步原子性和任务身份**四个边界钉死；继续加抽象，反而会让一次五项 bounded fix 开始长成第二套系统。
