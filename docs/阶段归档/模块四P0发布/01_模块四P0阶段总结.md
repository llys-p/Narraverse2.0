# Narraverse 模块四 P0 阶段总结

## 1. 这一阶段为什么开始

Module3 是已有的叙事/冒险工作流，重点是让模型继续写出内容；Module4 则要成为一个可以自己运行的开放沙盒文字 RPG。它不把玩家输入直接当成剧情事实，而是先把玩家行为放进世界规则里，再让时间、人物日程、关系和后果发生变化。

P0 要解决的核心问题只有一句话：

> 世界会自己运行，而且玩家能够改变它。

落实到体验上，就是玩家创建一个世界，加入角色，看到角色在一天中的安排，选择移动、聊天、帮助、邀请或探索等行动；系统依据当前时间、地点、日程、关系和风险推进结果，晚上结算并进入下一天。刷新或重启后，世界仍保持在正确状态。

## 2. 最终做成了什么

Module4 现在是一套独立的开放沙盒运行时。玩家可以创建多个世界，填写世界说明和自己的身份，加入已有角色资料。加入世界时会保存该角色的来源快照；之后源角色卡被修改或删除，也不会悄悄改写这个世界。

每个世界拥有自己的 NPC Runtime。角色的心情、关系、短期目标、临时状态和日程都属于当前世界，不会回写角色卡。每天分为早、中、晚三个时段，Daily Preview 为重要 NPC 生成三段短日程和世界事件骨架，而不是生成一篇长剧情。

玩家可以在地点之间移动，也可以主动寻找 NPC。是否遇见人物只取决于玩家当前地点、当前时段和 NPC 的当前有效日程；没有遇见是正常结果。推荐行动和自由输入统一进入 Action 管线，移动也通过同一管线扣精力、推进时间并返回相遇结果。

有阻力或风险的邀请、说服、请求帮助、探索和高风险行动会经过 Judgment，得到 `success`、`costly_success`、`failure` 或 `critical_failure` 四档结果。成功邀请可以改写当天后续日程，系统保留原计划和改写来源。失败不会直接 Game Over。

系统还会记录关键 Facts、当天互动 NPC 和简短 dailyLogs。晚间主要行动完成后，Settlement 作为唯一跨日入口，整理未互动人物、保存日志、清理临时状态、保留长期事实、恢复精力并进入次日早晨。连续多日和刷新恢复已经通过回归验证。

Module4 可以作为 standalone Narraverse 页面运行，也可以被 Denova 以同源 iframe 嵌入。它复用 Narraverse 已有的 `window.callLLM()` 和共享 `state.apiConfig`；真实模型 Preview 已完成非 fallback 验证，并在其上执行过 Action 和刷新恢复。

## 3. 明确没有做什么

P0 有意没有做以下内容：完整战斗、复杂技能树、传统 d20 骰子、多人联机、分钟级时间线、完整对白生成、长期记忆/向量库、独立 Module4 API 设置、独立 Go gameplay backend，以及新的 P1 玩法。

叙界旧 Director Console / 导演台不属于 Module4 的产品入口；Module4 也没有复制 Module3 的 Adventure/Game Engine 或固定响应协议。

## 5. 发布阶段的关键经验

### Clean Release Worktree

没有直接拿 `<project-root>` 发布，是因为该目录存在大量用户未提交修改。独立 release worktree 从正式 `origin/main` 建立，避免把用户改动、生成物或旧构建结果混入发布。发布过程中原始工作树保持只读，未执行 reset、clean、stash、restore 或覆盖。

### Denova 正式入口缺失

干净 checkout 的正式构建暴露出根目录 `.gitignore` 中的 `denova/` 规则误伤了 `denova-src/cmd/denova/`。开发目录可以依赖本地旧产物运行，但干净发布树无法编译正式入口。PR #13 将忽略规则锚定为 `/denova/`，恢复经过审计的入口文件，并补齐正式构建链路。

### Go embed 与头像文件名

普通 Web 静态服务可以接受头像文件名中的全角括号，但 Go `embed` 的正式构建对路径兼容性更严格。最终将 17 个头像文件从全角括号改为 ASCII 括号，保持图片字节不变；同时让 `gen_local_library_v2.py` 使用相同的文件名规范化，避免生成的角色卡引用旧路径。最终头像、Module4、dist、embed 和 release output 的资源哈希均一致。

### Task 10 暴露的集成问题

Task 10 期间先后验证并处理了 Module4 静态目录漏同步、iframe 旧缓存、生成器硬编码工程路径、页面滚动、共享 API 初始化、模型返回不满足 Preview validator、Prompt 合约不足和浏览器 origin/localStorage 隔离。最终真实共享模型调用通过现有 transport 完成，Preview 非 fallback，后续 Action 与刷新恢复成立。

## 6. 形成的工作方法

开发流程是：需求 → 架构边界 → bounded Task → 独立分支 → PR → 复审修复 → 合并。

发布流程是：确认 main → clean release worktree → 生成 local library → 静态同步 → 文件列表与 SHA-256 → frontend build → Go build → 官方 build.sh → executable smoke → shared API → real Preview → Action → 完整重启恢复 → Module3 保护检查 → tag。

“开发测试通过”只说明代码在开发基线下工作；只有正式构建产物、真实共享模型链路、持久化和宿主集成都通过，才可以称为 Production Ready。

## 7. 当前仍存在的限制

1. Windows 下如果开发服务器占用目标目录，现有静态资源同步的 atomic rename 可能出现 `EPERM`；已验证 staging snapshot 可以安全恢复，资源可以重新核对一致。
2. Denova 前端仍有 8 个既有 baseline failures；Module4 相关宿主定向测试通过，本阶段没有顺手修复旧基线。
3. Module4 P0 使用 localStorage 保存 Runtime、Facts 和 dailyLogs；大量长期记录的容量治理留给后续阶段。
4. 不同浏览器或不同 origin 的 localStorage 不共享，因此 `workspace` 书籍可以相同，但 Module4 世界列表需要在对应浏览器中重新创建或另行导入。
5. 当前正式 `module4-p0` tag 尚未在远端创建；这属于发布行政收口，不是已发现的 Module4 业务阻塞。

## 9. 下一阶段建议

先实际玩一段时间，记录“看不懂、找不到、信息太密、结果不清楚”的地方，把体验问题按频率和影响排序。当前用户已经指出整体表达较混乱，这应优先作为 P0 体验评估，而不是立刻叠加更多玩法。

之后再决定是先整理 Module3、先改善 Module4 信息呈现，还是进入 P1。无论选择哪条路，都应保留本阶段的 Module4/Module3 边界和真实发布回归基线。
