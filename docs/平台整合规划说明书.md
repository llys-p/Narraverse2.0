## 0. 摘要（Executive Summary）

将「文字冒险平台」（纯前端 SPA，强对话体验）与「Denova」（Go 全栈，强写作工程化与游戏模式）整合为**统一大平台**：以「**统一外壳 + 双引擎**」为骨架，外壳 **iframe 内嵌 Denova Web** 承载写作/游戏 UI 表面，三通道（iframe / HTTP API / 桥接服务）打通数据与交互；保留并突出各自特色，通过共享数据层与**纯本地**用户系统实现「写作驱动对话、游戏进度关联对话」的协同闭环。

> **本版锁定 4 项关键决策（2026-08-12 用户拍板）**：
> 1. **统一外壳 = iframe 内嵌 Denova Web**（非跳转）；
> 2. **纯本地，不做云端同步**（账号 = 本地 Profile，换机靠导出/导入）；
> 3. **视觉取第三套中性系统**为默认基线（非平台暗色游戏风，亦非 Denova 安静克制；二者降为可选主题）；
> 4. **导演台入口 = 右栏 Tab**，并内置**多场景预设**让功能按使用逻辑显隐（治「工具杂乱」）。

## 1. 整合目标与背景

### 1.1 整合动机
1. **用户旅程断裂**：创作者在平台跑灵感、在 Denova 做严肃长篇，两工具数据不互通、界面不统一，切换需手动导出/导入，上下文反复丢失。
2. **能力重复建设**：设定管理、章节/小说生成、图像、版本等重叠功能各做各的，质量参差。
3. **特色未被放大**：平台「对话爽感」与 Denova「工程化深度」各自为政，无法在同一作品里同时享受。

### 1.2 预期收益
| 维度 | 说明 |
|---|---|
| 创作闭环 | 对话灵感 → 写作成稿 → 游戏化发布，一处完成，数据全程贯通 |
| 能力互补 | 平台对话体验 + Denova 大纲/审稿/版本，短板补齐 |
| 维护降本 | 重叠功能去重，仅保留更优实现 |
| 用户留存 | 单一入口、统一视觉、场景化引导，降低学习成本 |

### 1.3 整体愿景
> **「一个作品，三种姿态，按场景组织功能」**：用户在同一统一平台中，以**对话**探索剧情、以**写作**沉淀成稿、以**游戏**体验互动；功能不堆叠，按当前创作场景**预设**自动显隐。

### 1.4 重合内容比较与优化空间（实地核验版）
| 域 | 平台现状（实地） | Denova 现状（实地） | 优化空间 |
|---|---|---|---|
| 写作与创作 | 一键生成小说（10 回合一章、保留文风）、Pixiv 配图 | Markdown 编辑器、大纲/细纲/审稿（novel-lite/standard/heavy）、Change Review、小说导入 | **去重**：生成归平台，审稿/大纲/版本归 Denova |
| 剧情与叙事 | 对话协议 `[NARRATIVE][STATE][CHOICES][PLOT]`、IF 线、好感/任务、上下文压缩 | 互动叙事（story_turn_narrative/turn_submission/history_search）、分支/故事线/行动建议/回复修正 | **协同**：平台 IF 线/好感度作 Denova 游戏剧情状态源 |
| 故事导演 | 场景图、World Info、**掷骰体系（parseDiceNotation/rollDiceNotation，d20）**、随机事件 | 导演台（director_plan）、Actor State、事件卡包、TRPG 检定 | **互通+融合**：复用 Denova 18 导演预设为初始库；检定交互走平台掷骰 UI |
| 角色与设定 | 知识库 50 设定 + 39 角色卡、chub、PNG 解析、NSFW/讲述者分类、Obsidian | lore items.json（resident/auto/manual）、CharacterCardImportDialog | **互通**：lorebook 双向同步（已实现 denova_lore_sync）；角色卡走 Denova 原生导入 |
| Agent 与自动化 | 无 Agent 层，LLM 直调 | Agent/SubAgent、18 Skills、审稿子流程、自动化 | **协同**：平台对话侧调用 Denova 审稿/扩写 Agent |
| 上下文与性能 | 压缩摘要、World Info 命中、设定解析缓存 | context-compaction、ContextAnalysis、token 用量、渐进式加载 | **互通**：统一上下文抽象，不互相复制机制 |
| 版本与恢复 | IndexedDB 存档、快照、IF 线存档、存储体检 | VersionPanel/ChangesList、本地 Git、changes/ledger.jsonl + blobs | **去重+升级**：平台快照升级为对齐 ledger.jsonl 的变更账本 |
| 图像 | AI 场景图、Pixiv 搜图、成图保存、ai-images | chapter-illustration、interactive-image、封面、图像预设 | **互通**：平台成图作 Denova 章节插画来源 |

## 2. 用户偏好与定位

整合后**不做均质化**，而是「一个入口、三种姿态、各自突出、按场景组织」。

### 2.1 文字冒险平台姿态（对话优先）
- **核心人群**：剧情党、角色扮演玩家、灵感探索者。
- **保留特色**：即时对话爽感、角色卡/设定一键挂载、对话协议叙事、IF 线、场景图/Pixiv 一体化、AI 写手思考过程可视化。
- **整合中职责**：「**剧情探索与体验层**」，产出世界观/角色/剧情状态，供上游写作、下游游戏消费。

### 2.2 Denova 姿态（写作/游戏优先）
- **核心人群**：长篇作者、世界观架构师、硬核玩家。
- **保留特色**：写作 IDE、大纲→细纲→章节三级管线、审稿子流程、版本账本、游戏模式与导演台。
- **整合中职责**：「**成稿与工程化层**」+「**互动游戏层**」，消费对话产出，产出可发布成稿与可玩游戏。

### 2.3 统一后的定位原则
- **不互相取代**：对话模块不内置完整写作 IDE，写作模块不重造对话协议。
- **特色可见**：统一外壳中对话/写作/游戏为并列一级入口。
- **渐进披露 + 场景驱动**：深层功能（导演台/大纲/版本）默认折叠，由**场景预设**按需显隐（见 §4.7），治「工具杂乱」。

## 3. 平台架构规划

### 3.1 总体架构决策（关键 · 已锁定）

采用 **「统一外壳 + 双引擎 + 三通道」** 模式，不 fork Denova：

- **统一外壳（Shell）**：纯前端，负责导航、本地 Profile、视觉主题、命令面板、跨模块状态桥、**iframe 宿主**。
- **对话引擎**：平台 `app.js`（在线 LLM 冒险 + 离线 `game_engine.js`），直接运行于外壳同源上下文。
- **写作/游戏引擎**：Denova（Go 后端 :8080 + React Web），**由外壳以 iframe 内嵌**承载其 UI 表面。

**三通道通信（v4 新明确）**：

```
┌──────────────── 统一外壳 Shell（前端，:8099 / file）────────────────┐
│  顶栏 · 侧栏作品树 · 命令面板(Ctrl/Cmd+K) · 本地 Profile · 场景预设   │
│  ┌──────────────┐         ┌──────────────────────────────┐          │
│  │ M1 对话模块    │         │ iframe：Denova Web（:8080）   │          │
│  │ app.js 同源    │         │ 写作 IDE / 游戏模式 UI 表面     │          │
│  └──────┬───────┘         └──────────┬───────────────────┘          │
└─────────┼─────────────────────────────┼──────────────────────────────┘
          │ 通道B：HTTP API(:8080)       │ 通道A：postMessage（跨 iframe）
          │ 数据读写/作品/章节/版本        │ 场景切换/作品切换/状态同步/命令
          │                              │
          │              通道C：桥接服务(:8097)
          │              denova_bridge.py（已落地 v3：设定/角色/摘要/章节/全文/进度条）
          └──────────────┴──────────────► Denova 本地工程 + lore/items.json
```

- **通道 A（postMessage）**：外壳 ↔ iframe 内 Denova Web 的**命令/事件**通道（切场景、切作品、请求状态、跳转章节）。因 iframe 跨源（外壳:8099 ↔ Denova:8080），不能直接读 DOM，必须走 `window.postMessage` + `MessageChannel`，Denova 侧暴露一个轻量 message adapter（见附录 E 契约草案）。
- **通道 B（HTTP API :8080）**：外壳直接调 Denova 已有/扩展的本地 HTTP 接口做**数据读写**（作品、章节、版本、lore）。
- **通道 C（桥接 :8097）**：一键导出/导入（`denova_bridge.py` v3 已落地），长任务走进度条。
- **理由**：iframe 内嵌让写作/游戏 UI **就地呈现**，切换不跳页、状态不丢；三通道分离关注点（UI 表面 / 数据 / 批量导出），互不侵入。

> 备选（仅记录，不推荐）：(b) fork Denova 把对话做成其剧情模式——成本高；(c) 平台全量自研写作/游戏——重复造轮子。

### 3.2 模块划分
```
统一大平台（统一外壳 Shell · iframe 宿主）
├── M1 文字对话模块  ← 平台 app.js（在线冒险线 + 离线小说线）
├── M2 写作模块      ← iframe 内嵌 Denova 写作 IDE + 平台小说生成（协同）
├── M3 游戏模式模块  ← 平台 game_engine.js + iframe 内嵌 Denova 互动叙事/导演台（协同）
├── M4 共享用户系统  ← 纯本地 Profile + 偏好 + 作品归属（无云端）
├── M5 数据层        ← 统一数据模型 + 存储抽象 + lorebook 适配器
└── M6 导航结构      ← 顶栏/侧栏/命令面板/三态切换 + 右栏 Tab（含导演台）+ 场景预设引擎
```

### 3.3 各模块职责
- **M1 文字对话模块**：对话协议解析、上下文压缩、IF 线、角色/状态追踪、AI 写手思考过程、场景图。产出「对话快照」（世界观增量、角色状态、剧情摘要）。
- **M2 写作模块**：iframe 内嵌 Denova 写作 IDE；大纲/细纲、章节生成、审稿、版本账本、小说导入导出。消费对话产出作初稿素材。
- **M3 游戏模式模块**：平台离线线（事件图/检定/战斗/结局）+ iframe 内嵌 Denova 互动叙事/导演台/状态机。消费对话状态作剧情状态源。
- **M4 共享用户系统**：**纯本地 Profile**（昵称/默认模型/主题/NSFW 开关/当前场景预设），跨模块偏好、作品归属。**无云端**；换机靠 Profile 单文件导出/导入（见 §5.2）。
- **M5 数据层**：统一实体（作品/设定书/角色卡/存档/章节/游戏进度）；存储抽象（平台 IndexedDB + Denova 本地文件，经适配器读写）；lorebook 标准化（items.json v2 ↔ 平台 entries）。
- **M6 导航结构**：统一顶栏（对话/写作/游戏/资料库/设置）、侧栏（作品树）、命令面板升级为跨模块 Jump（**按当前场景预设过滤**）、三态切换保活；**右栏 Tab 含「导演台」位**（见 §4.7）；场景预设引擎驱动功能显隐。

## 4. 功能整合方案

### 4.1 整合策略三分类
| 策略 | 含义 | 适用 |
|---|---|---|
| **去重** | 仅保留更优一方实现，另一方入口跳转 | 小说审稿/版本、设定管理 UI |
| **互通** | 数据双向同步，格式经适配器转换 | 设定书/角色卡/lore、章节、版本账本 |
| **协同** | 一方产出驱动另一方行为，形成闭环 | 写作驱动对话、游戏进度关联对话 |

### 4.2 现有功能梳理与处置
- **设定管理**：去重——UI 统一到平台知识库入口；互通——`denova_lore_sync` export/import 固化为实时双向同步。
- **小说生成**：去重——「生成」用平台，「大纲/审稿/版本」用 Denova；协同——生成结果一键送入 Denova 写作模块（已实现：分章 + 小说全文.txt + 中文设定文档）。
- **对话叙事**：协同——平台 IF 线/好感度/任务 → 映射为 Denova 游戏剧情状态。
- **导演台**：互通+融合——复用 Denova 18 导演预设为初始库；**检定交互对接平台掷骰 UI（parseDiceNotation/rollDiceNotation/dice 菜单），Denova rule-systems 提供难度/风格模板**。
- **图像**：互通——平台成图写入共享 ai-images，Denova 章节插画可直接引用。
- **版本**：去重+升级——平台快照升级为对齐 Denova ledger.jsonl + blobs 的变更账本，前端可借鉴 ChangesList。

### 4.3 协同逻辑一：写作内容驱动文字冒险
```
写作模块产出（世界观/章节/角色草稿）
   → 数据层适配为平台设定书 entries / 角色卡
   → 对话模块「加载设定」一键挂载（gatherLoadItems）
   → 对话协议 [NARRATIVE][STATE] 直接消费，剧情即刻拥有写作侧厚重背景
```

### 4.4 协同逻辑二：游戏进度关联对话
```
游戏模式产出（事件图节点/检定结果/好感度/任务状态）
   → 映射为对话模块 STATE 协议字段
   → 对话模块据 STATE 生成分支选项与剧情推进
   → 对话选择回写游戏进度（闭环）
```
- 实现：平台离线线 `game_engine.js` 已产出事件/检定/数值；对话线 `[STATE]` 已承载好感/任务；字段对齐即可双向流转。

### 4.5 统一数据模型（草案）
| 实体 | 平台现有 | Denova 现有 | 统一表示 |
|---|---|---|---|
| 作品 Work | 冒险 adv（IndexedDB） | 工程 projects/<name> | work{id, title, mode, created, updated} |
| 设定书 Book | ai知识库/世界观设定/*.json（entries） | lore/items.json（items） | 适配器互转 |
| 角色卡 Card | SillyTavern v2 | 原生导入 / lore character | 统一 SillyTavern v2 |
| 存档 Save | IndexedDB 快照 | Git 版本 | 变更账本（ledger.jsonl） |
| 章节 Chapter | 小说生成章节 | Markdown 章节 | 统一章节树 |

### 4.6 平台可复用资产清单（实地盘点，防重复建设）
- 掷骰体系（d20 属性检定、随机事件、战斗行动）
- 命令面板 Ctrl/Cmd+K、右栏 Tab、抽屉布局（Agent/时间轴/曼陀罗/地点）
- 进度条/阶段反馈（denovaExportModal，可推广至所有长任务）
- World Info 注入（与 Denova lore auto 语义对应）
- PNG 角色卡解析（extractCharaFromPNG）、chub 导入
- 知识库生成管线（gen_local_library）、Obsidian 素材库

### 4.7 场景化预设（v4 新增 · 治「工具杂乱」核心机制）

**问题**：Denova 工具多被吐槽；平台右栏 Tab 也在增长（状态/属性/技能/背包/关系/任务/导演台）。功能平铺 = 杂乱。

**机制**：**场景预设 = 创作场景 → 功能显隐/默认值的命名配置**，随 Work 保存。切场景即重组界面，让功能按使用逻辑出现，而非全量堆叠。

**预设的数据结构**：
```
Preset {
  id, name, icon,
  defaultModule: 'dialogue' | 'writing' | 'game' | 'library',
  rightTabs:   ['status','attr','skill','inventory','relation','quest','director'],  // 可见集
  directorFields: ['goal','pressure','cost','events','check','state'],               // 导演台显字段
  cmdFilter:   ['dialogue.*','writing.*', ...],                                       // 命令面板过滤
  visualDensity: 'compact' | 'normal' | 'spacious',
  autoLaunch:  ''                                                                      // 进入 Work 自动执行
}
```

**内置 5 个预设（首期交付）**：

| 预设 | 人群/场景 | 默认模块 | 右栏可见 Tab | 导演台字段 | 命令面板过滤 | 视觉密度 |
|---|---|---|---|---|---|---|
| **灵感探索** | 剧情党·灵感期 | 对话 | 状态、关系、导演台 | 目标、压力（轻量） | 对话+设定 | spacious |
| **严肃长篇** | 作者·成稿期 | 写作 | 导演台、关系、任务 | 全字段 | 写作+版本+设定 | normal |
| **互动游戏** | 玩家·游玩期 | 游戏 | 状态、技能、导演台 | 事件、检定、状态 | 游戏+检定 | compact |
| **快速试玩** | 新用户/分享 | 对话 | 状态 | （隐藏导演台） | 仅对话 | spacious |
| **世界观构建** | 架构师·设定期 | 资料 | 导演台、属性、关系 | 规则、lore | 设定+规则 | normal |

- **导演台入口 = 右栏 Tab**：与状态/属性/技能/背包/关系/任务并列，复用平台已有右栏 Tab 化基础设施（`switchRightTab`）；不再单列全屏弹窗为主入口（全屏态作为导演台 Tab 内的「展开」二级动作保留）。
- **用户可自定义预设**：基于内置预设派生，随 Work 持久化（M5）。
- **命令面板按预设过滤**：`openCommandPalette` 已落地，扩 `cmdFilter` 维度，输入即达当前场景相关命令。
- **首次引导**：新建作品时按「姿态」选预设，仅展示对应入口，降学习曲线。

## 5. 用户体验一致性

### 5.1 视觉风格统一（第三套中性系统 · 已锁定）
- **决策**：不取平台暗色游戏风，不取 Denova 安静克制，**取第三套中性系统「工作室中性」为默认基线**；平台原暗色游戏风、Denova 原安静克制**降为可选主题**。
- **「工作室中性」令牌（草案）**：
  - **色阶**：中性灰阶 `--neutral-0..1000`，背景非纯黑非辉光（如 `#1a1c20`），文本高对比达 WCAG AA；
  - **语义色**：仅 3 主色（信息/成功/警示/错误），低饱和，避免双色辉光喧宾夺主；
  - **字体**：Inter（双方已统一），中文回退 PingFang/YaHei；
  - **可读优先**：content-first 排版（吸收 Denova 安静），行高/字距为长文优化；
  - **克制动效**：仅过渡/焦点态，默认 `prefers-reduced-motion` 关辉光；
  - **组件**：统一 `.btn`/`.card`/`.modal`/`:focus-visible` 焦点环。
- **落地方式**：新建 `theme-neutral.css` 作为外壳与 Denova Web 共享基线；平台 `redesign.css`、Denova 原主题改为可切换主题层叠加其上。

### 5.2 账号体系统一（纯本地 · 已锁定）
- **决策**：**纯本地，不做云端同步**。
- 「共享用户系统」= **本地 Profile**（JSON，存 IndexedDB）：昵称/头像/默认模型配置/主题选择/当前场景预设/NSFW 开关。
- **换机同步**：Profile 单文件导出/导入（`.workbuddy-profile.json`），无服务器；作品随导出包一并迁移。
- **远程访问**：沿用 Denova 本地网络/PWA 能力（局域网内），不引入公网账号。

### 5.3 操作流统一（场景驱动）
- 全局命令面板（已落地 `Ctrl/Cmd+K` `openCommandPalette`）升级为**跨模块 Jump**，**按当前场景预设 `cmdFilter` 过滤**。
- 统一顶栏与侧栏（作品树），三态切换**保持模块状态不卸载**，切换即续。
- 右栏 Tab 集随场景预设变化（§4.7），导演台为其中之一。
- 统一快捷键、统一空状态/加载/错误文案语气。

### 5.4 切换顺畅性
- 切换模块时当前状态快照入 M5 数据层，目标模块从同一 Work 恢复上下文，做到「切回去还在原处」。
- iframe 内 Denova Web 切场景/作品通过 postMessage 通知，Denova 侧 message adapter 响应（附录 E）。

## 6. 阶段性实施路线

> 原则：平台保持轻量主流程不变；深层能力渐进披露。每阶段可独立验收、可回退。
> 与《结合方案》里程碑对齐：P0/P1≈Step0/0b，P2≈导演台+场景预设，P3≈写作与版本，P4≈体验统一。

| 阶段 | 目标 | 优先级 | 关键交付 | 验收标准 |
|---|---|---|---|---|
| **P0 基础** | iframe 外壳 + 三通道 + 本地 Profile | 高 | iframe 嵌 Denova Web；postMessage 契约（附录 E）；M5 数据模型+适配器；M6 导航/命令面板；M4 纯本地 Profile | 外壳三入口可切；iframe 内 Denova 可交互无跨源报错；设定书双向同步无丢失；偏好跨模块生效 |
| **P1 对话固化** | 对话模块定型 + 写作↔对话互通 | 高 | `gatherLoadItems` 接入写作侧成稿；一键「对话→Denova 工程」完善为实时 | 写作成稿一键挂载进对话并即时叙事；导出工程 Denova 可读（现有 exportToDenova + 进度条已达标） |
| **P2 导演台 + 场景预设** | 导演台右栏 Tab + 5 内置预设 | 高 | 导演台作右栏 Tab（复用 `switchRightTab`）；5 场景预设引擎（§4.7）；命令面板 `cmdFilter` | 导演台为右栏 Tab；5 预设可切；功能按场景逻辑显隐；检定走平台掷骰 UI |
| **P3 写作工程化** | 大纲/审稿/版本引入 | 中 | 平台小说生成接 Denova 大纲/审稿；快照升级为变更账本 | 生成小说可进大纲修订 + 版本 Diff/回滚 |
| **P4 视觉统一** | 第三套中性系统落地 | 高 | `theme-neutral.css` 共享基线；平台/Denova 原主题降为可选；统一文案/快捷键；状态保活切换 | 中性基线全模块生效；两 originals 可选主题；切换无状态丢失；WCAG AA 达标 |
| **P5（低/可选）** | 换机迁移 + 局域网远程 | 低 | Profile 导出/导入（含作品）；远程访问沿用 Denova PWA | 换机作品同步；局域网移动端可访问 |

**建议首期范围**：**P0 + P1 + P2**（外壳 iframe + 对话互通 + 导演台/场景预设）。三者合一即让用户感知「一个入口、数据贯通、功能按场景组织」，且 P2 直接命中用户对「工具杂乱」的核心痛点。P4 视觉统一可并行起步（令牌先行）。

## 7. 风险与备注

### 7.1 技术风险
| 风险 | 影响 | 应对 |
|---|---|---|
| **iframe 跨源限制** | 外壳:8099 ↔ Denova:8080 跨源，无法直读 DOM | 走 postMessage + MessageChannel 契约（附录 E）；Denova 侧加轻量 message adapter；数据操作走通道 B HTTP API |
| **postMessage 契约维护** | 双方版本不一致导致命令丢失 | 契约版本化（`msg.ver`），adapter 拒绝未知命令并回错；契约纳入回归测试 |
| 双引擎并存复杂度 | 外壳对接纯前端 + Go 后端 | 通道分离：UI 表面走 iframe、数据走 HTTP API、批量走桥接；外壳不侵入引擎逻辑 |
| 数据格式差异 | lore items.json ↔ 平台 entries | M5 单向可信适配器 + 回归测试（denova_lore_sync 已落地，补双向自动化测试） |
| 实时性冲突 | 对话 SSE 流式 vs 写作静态 | 写作→对话「挂载即消费」；对话→写作「摘要同步」，避免流式强耦合 |
| IndexedDB 容量 | 版本账本/图片膨胀 | 沿用「存储体检」；blob 差异存 blobs/，账本仅存索引 |
| **中性视觉迁移成本** | 双方都要改主题层 | 令牌先行：先建 `theme-neutral.css` 基线，双方原主题作可选层叠加，不一次性重写 |
| 移植范围失控 | Denova interactive 模块庞大（100+ 文件） | 只移植「导演台 + 检定规则」子集，其余按需引入 |
| Denova 升级兼容 | Denova 迭代改 lore/API 结构 | 适配器锁定 items.json v2 契约，升级时仅改适配器 |

### 7.2 体验风险
| 风险 | 影响 | 应对 |
|---|---|---|
| 工具杂乱 | 用户已吐槽 Denova 工具多 | **场景预设**（§4.7）按场景显隐；默认只显三入口；深层功能折叠 |
| 切换打断心流 | 对话/写作思维不同 | 状态保活切换；命令面板按场景过滤直达；不强制线性流程 |
| 学习曲线 | 新用户面对双能力 | 首次引导按「姿态」选预设，仅展示对应入口 |
| iframe 加载闪烁 | 切模块时 iframe 重载 | Denova Web 常驻 iframe，切场景仅 postMessage 通知，不重载页面 |

### 7.3 备注
- **不 fork Denova**：维持其 Apache-2.0 独立演进，整合层仅做适配与导航。
- **已有资产复用**：`denova_lore_sync.js`、`denova_bridge.py`（v3）、`exportToDenova()`、`redesign.css`、命令面板、掷骰体系均已落地，P0/P1/P2 可直接推进。
- **路径常量**：Denova 安装路径统一 `<external-denova-installation>`；所有脚本/常量不得写死旧 `<legacy-denova-root>`。
- **协作铁律**：落地涉及代码改动时，按 `项目协作日志.md` 铁律追加倒序日志并同步 `代码指南.md`；导出走「内容治理」原则（摘要生成/筛选/去重/中文化）。

## 附录 E · postMessage 桥接契约草案（v4 新增）
外壳（Shell）↔ iframe（Denova Web）双向通信，统一信封：
```json
{
  "ver": 1,
  "src": "shell" | "denova",
  "id": "<uuid>",
  "type": "request" | "event" | "response",
  "cmd": "switch-scene" | "open-work" | "jump-chapter" | "sync-state" | "query-status",
  "payload": { ... },
  "ts": 1694820000000
}
```
- **cmd 清单（首期）**：`switch-scene`（切场景预设）、`open-work`（切作品）、`jump-chapter`（跳章节）、`sync-state`（对话↔游戏状态同步）、`query-status`（外壳查 Denova 当前态）。
- **安全**：双方校验 `e.origin`（白名单 `http://localhost:8099` / `http://localhost:8080`），拒未知 `cmd` 并回 `{type:"response", ok:false, err:"unknown-cmd"}`。
- **Denova 侧落地**：在其 React 入口加一个 `messageAdapter` 订阅 `message` 事件，路由到对应 workbench/interactive action；不侵入其业务逻辑，仅做命令翻译层。
- **契约版本化**：`ver` 字段锁版本，升级走双写兼容期。
