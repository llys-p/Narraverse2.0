## 二、v2 对 v1 的关键修正

1. **"Denova 弱在剧情对话体验"表述修正**：实地读 interactive 模块（100+ Go 文件：director_plan/turn_submission/story_turn_narrative/tellers/rule_state_consumption/history_search/opening_state_initialization）证明 Denova 的"剧情工程化"能力远比此前认知强——它弱的不是剧情能力，而是**即时对话的轻量入口**。整合重点从"给平台补剧情"微调为"把 Denova 的导演/状态机能力以轻量方式暴露到平台对话流"。

2. **导演台移植范围收敛**：v1 说"复用七套题材预设"；实地确认 preset 共 **18 个文件**（actor-states 5 + event-packages 7 + rule-systems 6），且 interactive 模块庞大。v2 明确"只移植 导演台+检定规则 子集，其余按需引入"，避免移植失控。

3. **发现平台已有掷骰体系**：v1 未提；实地发现平台已有 parseDiceNotation/rollDiceNotation/dice 菜单/随机事件（d20 检定）。v2 将 Denova 检定定位为"规则模板来源"，交互走平台现有 dice UI——**融合而非另起炉灶**，这是 v1 缺失的关键复用点。

4. **发现 Denova 原生导入通道**：CharacterCardImportDialog（酒馆卡导入）与 NovelImportDialog（小说导入）在 web/src 实地存在——角色卡互通 v1 只提"原生支持"，v2 落到具体组件，且导出章节时可直接利用。

5. **版本账本前端证据**：Denova VersionPanel/ChangesList/AutoSummary 实地存在，v2 明确 Step3 可借鉴其 ChangesList 交互。

6. **平台资产盘点更完整**：v1 未列 命令面板 Ctrl+K / 右栏 Tab / 抽屉布局 / PNG 卡解析 / World Info 注入 等可复用资产；v2 单列 4.3 节，作为防重复建设清单。

7. **Denova 工程规模数据**：v2 核验本地 10 个工程（老板 101 条 lore 等），说明数据互通已有真实负载，M5 深度协同有现实基础。

## 三、v1 中仍成立、v2 保留的内容

- 整合方向："平台轻量入口 + 深度能力渐进披露"（v1 结论，v2 保持）。
- 里程碑顺序 M0（已完成）→ M1 导演台 → M2 写作工程化 → M3 版本账本 → M4 视觉统一 → M5 深度协同（v2 沿用，M1 内容按修正 2/3 调整）。
- 单一可信源原则、NSFW 开关为准、敏感凭据本地保管、"内容治理"导出原则。

## 四、待确认/开放问题

1. 导演台移植的交互入口：独立弹窗 vs 右栏 Tab（平台已有 4 抽屉）——倾向右栏 Tab 复用。
2. 检定规则：是否全量引入 Denova 6 种 DM 风格，还是先映射 2-3 种高频风格（drama-stakes/fail-forward/default）。
3. M2 审稿：novel-standard 审稿子流程在平台是否值得引入（token 成本 vs 质量收益）。

## 五、结论

v2（实地版）证据更扎实、修正了 v1 的两处重要误判（Denova 剧情能力定位、平台掷骰体系遗漏），并给出移植范围收敛与复用清单。建议以 **v2 为实施基准**，v1 作为背景参考。
