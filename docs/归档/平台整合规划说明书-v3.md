## 0. 摘要（Executive Summary）

当前「文字冒险平台」与「Denova」是两个定位互补但彼此割裂的本地创作工具：

- **文字冒险平台**：纯静态前端单页（SPA），强在**文字对话即时体验**——角色卡/设定一键挂载、对话协议驱动叙事、IF 线、场景图/Pixiv 一体化；但写作工程化能力薄弱（小说生成为一次性，无大纲/审稿/版本）。
- **Denova**：Go 单文件 + React Web 的**本地自托管 AI 创作工作室**，强在**写作工程化**（大纲→细纲→审稿→版本账本→Agent 自动化）与**游戏模式工程化**（导演台/回合状态机/事件系统/检定规则——interactive 模块 100+ Go 文件）；弱在**即时对话的轻量入口**（工具堆叠、流程偏重）。

本说明书将二者整合为**统一大平台**：以「**统一外壳 + 双引擎**」为骨架，保留并突出各自特色，通过共享数据层与用户系统实现「写作内容驱动对话、游戏进度关联对话」的协同闭环。既不重写 Denova（Go 全栈改造成本高），也不让平台无限膨胀，用一层薄整合层把已验证能力缝合为「创作—体验—发布」闭环。

> **实地核验（2026-08-12）**：本版关键判断均基于对两平台源码/运行态的实地阅读——平台 305 函数/40 分组/18 弹窗/4 抽屉；Denova 30 个 Go 模块/web 前端 20+ 功能面/18 个导演预设/本地 10 个工程。证据见附录 C。

## 1. 整合目标与背景

### 1.1 整合动机

1. **用户旅程断裂**：创作者常在平台跑剧情灵感，又需在 Denova 做严肃长篇；两工具数据不互通、界面不统一，切换需手动导出/导入，反复上下文丢失。
2. **能力重复建设**：双方均实现了设定管理、章节/小说生成、图像、版本等重叠功能，但各做各的，质量参差。
3. **特色未被放大**：平台的「对话爽感」与 Denova 的「工程化深度」各自为政，用户无法在同一作品里同时享受两者。

### 1.2 预期收益

| 收益维度 | 说明 |
| --- | --- |
| 创作闭环 | 对话灵感 → 写作成稿 → 游戏化发布，一处完成，数据全程贯通 |
| 能力互补 | 平台对话体验 + Denova 大纲/审稿/版本，短板补齐 |
| 维护降本 | 重叠功能去重（仅保留更优实现），减少双份维护 |
| 用户留存 | 单一入口、统一账号与视觉，降低学习成本与流失 |

### 1.3 整体愿景

> **「一个作品，三种姿态」**：用户在同一统一平台中，以**对话**探索剧情、以**写作**沉淀成稿、以**游戏**体验互动，三者共享同一套世界观、角色与进度，随时无缝切换。

### 1.4 重合内容比较与优化空间（实地核验版）

| 域 | 平台现状（实地） | Denova 现状（实地） | 优化空间（整合后） |
| --- | --- | --- | --- |

## 2. 用户偏好与定位

整合后**不做均质化**，而是「一个入口、三种姿态、各自突出」：

### 2.1 文字冒险平台姿态（对话优先）
- **核心人群**：剧情党、角色扮演玩家、灵感探索者。
- **保留特色**：即时对话爽感、角色卡/设定一键挂载、对话协议叙事、IF 线、场景图/Pixiv 一体化、思考过程可视化。
- **整合中职责**：「**剧情探索与体验层**」，产出世界观/角色/剧情状态，向上游写作模块与下游游戏模块供数。

### 2.2 Denova 姿态（写作/游戏优先）
- **核心人群**：长篇作者、世界观架构师、硬核玩家。
- **保留特色**：写作 IDE、大纲→细纲→章节三级管线、审稿子流程、版本账本、游戏模式与导演台。
- **整合中职责**：「**成稿与工程化层**」+「**互动游戏层**」，消费对话模块产出的素材，产出可发布成稿与可玩游戏。

### 2.3 统一后的定位原则
- **不互相取代**：对话模块不内置完整写作 IDE，写作模块不重造对话协议。
- **特色可见**：统一外壳中对话/写作/游戏为并列一级入口，各模块默认呈现最具代表性的能力。
- **渐进披露**：深层功能（导演台/大纲/版本）按需展开，避免「工具杂乱」。

## 3. 平台架构规划

### 3.1 总体架构决策（关键）

采用 **「统一外壳 + 双引擎」** 模式，而非 fork Denova：

- **统一外壳（Shell）**：纯前端，负责导航、账号/偏好、视觉主题、命令面板、跨模块状态桥。
- **对话引擎**：平台 `app.js`（在线 LLM 冒险 + 离线 `game_engine.js`）。
- **写作/游戏引擎**：Denova（Go 后端 + React Web），通过本地 HTTP API 与外壳通信。
- **理由**：Denova 为 Go 全栈、Apache-2.0，改造成本高；平台为无构建纯前端。用薄整合层缝合，风险最低。

> 备选方案（仅记录，不推荐）：(b) fork Denova 把对话做成其「剧情模式」——成本高；(c) 平台全量自研写作/游戏——重复造轮子。本说明书以 (a) 为准。

### 3.2 模块划分

```
统一大平台（统一外壳 Shell）
├── M1 文字对话模块  ← 平台 app.js（在线冒险线 + 离线小说线）
├── M2 写作模块      ← Denova 写作 IDE + 平台小说生成（协同）
├── M3 游戏模式模块  ← 平台 game_engine.js + Denova 互动叙事/导演台（协同）
├── M4 共享用户系统  ← 本地 Profile + 偏好 + 可选云端同步
├── M5 数据层        ← 统一数据模型 + 存储抽象 + lorebook 适配器
└── M6 导航结构      ← 顶栏/侧栏/命令面板（Ctrl/Cmd+K）/三态切换
```

### 3.3 各模块职责

- **M1 文字对话模块**：对话协议解析、上下文压缩、IF 线、角色/状态追踪、AI 思考过程、场景图。产出「对话快照」（世界观增量、角色状态、剧情摘要）。
- **M2 写作模块**：Markdown IDE、大纲/细纲、章节生成、审稿、版本账本、小说导入导出。消费对话模块产出的设定/摘要作为初稿素材。
- **M3 游戏模式模块**：事件图、检定、战斗、结局（平台离线线）；分支/故事线/导演台/状态机（Denova interactive）。消费对话模块状态作为剧情状态源。
- **M4 共享用户系统**：本地 Profile（昵称/默认模型/主题/NSFW 开关）、跨模块偏好、作品归属。
- **M5 数据层**：统一实体（作品/设定书/角色卡/存档/章节/游戏进度）；存储抽象（平台 IndexedDB + Denova 本地文件）；lorebook 标准化（items.json v2 ↔ 平台设定书 entries）。
- **M6 导航结构**：统一顶栏（对话/写作/游戏/资料库/设置）、侧栏（作品树）、命令面板升级为跨模块 Jump、三态切换保持模块状态不丢失。

## 4. 功能整合方案

### 4.1 整合策略三分类

| 策略 | 含义 | 适用 |
| --- | --- | --- |
| **去重** | 仅保留更优一方实现，另一方入口跳转 | 小说审稿/版本、设定管理 UI |
| **互通** | 数据双向同步，格式经适配器转换 | 设定书/角色卡/lore、章节、版本账本 |
| **协同** | 一方产出驱动另一方行为，形成闭环 | 写作驱动对话、游戏进度关联对话 |

### 4.2 现有功能梳理与处置

- **设定管理**：去重——UI 统一到平台知识库入口；数据互通——denova_lore_sync export/import 已落地，固化为「实时双向同步」。
- **小说生成**：去重——「生成」用平台（保留文风/Pixiv），「大纲/审稿/版本」用 Denova；协同——生成结果一键送入 Denova 写作模块（已实现：章节分章 + 小说全文.txt + 中文设定文档）。
- **对话叙事**：协同——平台 IF 线/好感度/任务 → 映射为 Denova 游戏模式剧情状态。
- **导演台**：互通+融合——复用 Denova 18 个导演预设为初始库；**检定交互对接平台现有掷骰 UI（parseDiceNotation/rollDiceNotation/dice 菜单），Denova rule-systems 提供难度/风格模板**。
- **图像**：互通——平台成图写入共享 ai-images，Denova 章节插画可直接引用。
- **版本**：去重+升级——平台快照升级为对齐 Denova ledger.jsonl + blobs 的变更账本，未来双向可读。

### 4.3 协同逻辑一：写作内容驱动文字冒险

```
写作模块产出（世界观/章节/角色草稿）
   → 数据层适配为平台设定书 entries / 角色卡
   → 对话模块「加载设定」一键挂载（gatherLoadItems）
   → 对话协议 [NARRATIVE][STATE] 直接消费，剧情即刻拥有写作侧的厚重背景
```

### 4.4 协同逻辑二：游戏进度关联对话

```
游戏模式产出（事件图节点/检定结果/好感度/任务状态）
   → 映射为对话模块 STATE 协议字段
   → 对话模块据 STATE 生成分支选项与剧情推进
   → 对话选择回写游戏进度（闭环）
```
- 实现基础：平台离线线 game_engine.js 已产出事件/检定/数值；对话线 [STATE] 已承载好感/任务；二者字段对齐即可双向流转。

### 4.5 统一数据模型（草案）

| 实体 | 平台现有 | Denova 现有 | 统一表示 |
| --- | --- | --- | --- |
| 作品 Work | 冒险 adv（IndexedDB） | 工程 projects/<name> | work{id, title, mode, created, updated} |
| 设定书 Book | ai知识库/世界观设定/*.json（entries） | lore/items.json（items） | 适配器互转 |
| 角色卡 Card | SillyTavern v2 | 原生导入 / lore character | 统一 SillyTavern v2 |
| 存档 Save | IndexedDB 快照 | Git 版本 | 变更账本（ledger.jsonl） |
| 章节 Chapter | 小说生成章节 | Markdown 章节 | 统一章节树 |

### 4.6 平台可复用资产清单（实地盘点，防重复建设）

- 掷骰体系（d20 属性检定、随机事件、战斗行动）
- 命令面板 Ctrl/Cmd+K、右栏 Tab、抽屉布局（Agent/时间轴/曼陀罗/地点）
- 进度条/阶段反馈（denovaExportModal，可推广至所有长任务）
- World Info 注入（与 Denova lore auto 语义对应）
- PNG 角色卡解析（extractCharaFromPNG）、chub 导入
- 知识库生成管线（gen_local_library）、Obsidian 素材库

## 5. 用户体验一致性

### 5.1 视觉风格统一
- 平台暗色游戏风（redesign.css，玻璃拟态/双色辉光/Inter 字体）建议作为统一设计令牌系统，外延至 Denova Web 端（Denova 原生「安静克制 content-first」，在其主题层叠加平台令牌，保留内容优先同时获得一致焦点态）。
- 统一组件：按钮、卡片、模态、焦点环、降级动效。

### 5.2 账号体系统一
- 现状：双方均本地、无服务端账号。整合后「共享用户系统」= 本地 Profile + 作品归属 + 偏好，不引入强制登录。
- 可选远期：Profile 导出/导入实现换机同步；远程访问沿用 Denova PWA/远程能力。

### 5.3 操作流统一
- 全局命令面板升级为**跨模块 Jump**（对话/写作/游戏命令同池）。
- 统一顶栏与侧栏（作品树），三态切换**保持模块状态不卸载**，切换即续。
- 统一快捷键、统一空状态/加载/错误文案。

### 5.4 切换顺畅性
- 切换模块时当前状态快照入 M5 数据层，目标模块从同一 Work 恢复上下文，做到「切回去还在原处」。

## 6. 阶段性实施路线

> 原则：平台保持轻量主流程不变；深层能力渐进披露。每阶段可独立验收、可回退。
> 与《结合方案》里程碑对齐：P0/P1≈M0+Step0/0b，P2≈M1 导演台，P3≈M2/M3 写作与版本，P4≈M4 体验统一。

| 阶段 | 目标 | 优先级 | 关键交付 | 验收标准 |
| --- | --- | --- | --- | --- |
| **P0 基础** | 数据层 + 统一外壳骨架 | 高 | M5 数据模型与适配器、M6 导航/命令面板、M4 本地 Profile | 外壳可切三入口；设定书双向同步无丢失；偏好跨模块生效 |
| **P1 对话固化** | 对话模块定型 + 写作↔对话互通 | 高 | gatherLoadItems 接入写作侧成稿；一键「对话→Denova 工程」完善为实时 | 写作成稿可一键挂载进对话并即时叙事；导出工程 Denova 可读（现有 exportToDenova + 进度条已达标） |
| **P2 游戏整合** | 游戏进度关联对话 + 导演台 | 中 | game_engine 状态 ↔ 对话 [STATE] 映射；导演台复用 Denova 18 个导演预设（对接平台掷骰 UI） | 游戏事件触发对话分支；对话选择回写游戏进度，闭环可玩；检定走平台 dice UI |
| **P3 写作工程化** | 大纲/审稿/版本引入 | 中 | 平台小说生成接 Denova 大纲/审稿；快照升级为变更账本 | 生成小说可进大纲修订 + 版本 Diff/回滚 |
| **P4 体验打磨** | 视觉/账号/切换一致 | 高 | Denova Web 叠加平台设计令牌；统一文案/快捷键；状态保活切换 | 三模块视觉一致；切换无状态丢失 |
| **P5 远期** | 云端同步/远程/多端 | 低 | Profile 导入导出、远程访问 | 换机作品同步；移动端可访问 |

**建议首期范围**：P0 + P1（基础骨架 + 对话与写作互通），即可让用户感知「一个入口、数据贯通」，风险与工作量可控。P2 导演台为剧情深度核心，紧随其后。

## 7. 风险与备注

### 7.1 技术风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 双引擎并存复杂度 | 外壳需同时对接纯前端与 Go 后端 | 定义稳定本地 HTTP API 契约；外壳只做导航/桥接，不侵入引擎逻辑 |
| 数据格式差异 | lore items.json ↔ 平台 entries 字段不对齐 | M5 单向可信适配器 + 回归测试（denova_lore_sync 已落地，补双向自动化测试） |
| 实时性冲突 | 对话 SSE 流式 vs 写作静态文档 | 写作→对话「挂载即消费」；对话→写作「摘要同步」，避免流式强耦合 |
| IndexedDB 容量 | 版本账本/图片膨胀超限 | 沿用「存储体检」；blob 差异存 blobs/，账本仅存索引 |
| **移植范围失控** | Denova interactive 模块庞大（100+ 文件） | 只移植「导演台 + 检定规则」子集，其余（tellers/回合提交/历史检索）按需引入 |
| Denova 升级兼容 | Denova 迭代改 lore/API 结构 | 适配器锁定 items.json v2 契约，升级时仅改适配器 |

### 7.2 体验风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 工具杂乱 | 用户已吐槽 Denova 工具多 | 统一外壳默认只显三入口；深层功能渐进披露，默认折叠 |
| 切换打断心流 | 对话/写作思维不同 | 状态保活切换；命令面板直达；不强制线性流程 |
| 学习曲线 | 新用户面对双能力 | 首次引导按「姿态」分流（对话党/作者党/玩家党），仅展示对应入口 |

### 7.3 备注
- **不 fork Denova**：维持其 Apache-2.0 独立演进，整合层仅做适配与导航。
- **已有资产复用**：denova_lore_sync.js、denova_bridge.py（v3：设定/角色/摘要/章节/全文/设定文档/进度条）、exportToDenova()、redesign.css、命令面板均已落地，P0/P1 可直接推进。
- **路径常量**：Denova 安装路径统一 <external-denova-installation>；所有脚本/常量不得写死旧 <legacy-denova-root>。
- **协作铁律**：落地涉及代码改动时，按项目协作日志铁律追加倒序日志并同步代码指南；导出走「内容治理」原则（摘要生成/筛选/去重/中文化）。
