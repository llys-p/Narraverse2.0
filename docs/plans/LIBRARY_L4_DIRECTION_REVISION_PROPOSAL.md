# L4 方向修订建议：从“旧资料迁移工程”改为“旧资料收口与可选导入”

日期：2026-09-27  
状态：**方向建议 / 交给后续 AI 评审，不代表已修改 L4 正式契约，不授权迁移、删除或改写用户资料。**

> 本文是对现有 `LIBRARY_L4_MIGRATION_PLAN.md` 的方向修订建议。  
> 后续 AI 在实施 L4 前必须先读：`LIBRARY_EVOLUTION_BLUEPRINT.md`、`LIBRARY_EVOLUTION_TASK_CHECKLIST.md`、`LIBRARY_L4_MIGRATION_PLAN.md` 和本文。  
> 若本文与当前正式契约冲突，以**尚未修改的正式契约为当前事实**；应先提出契约差异并获得用户确认，再改计划/清单/代码。

## 1. 为什么要重新考虑 L4

原 L4 的主要目标是：

> 把用户选中的旧 World 与作品 Lore 安全地转换为新 Library，并通过 inventory → preview → confirm → backup → apply → verify → rollback 完成旧系统收口。

这个设计本身在数据安全上是合理的，但随着 L1/L2 已成型、L3 准备让新 Library 直接服务四种模式，L4 的产品价值需要重新排序。

当前真正重要的目标已经不是“把旧数据全部迁完”，而是：

1. **新 Library 成为今后作品设定的唯一主要编辑入口。**
2. **L3 四模式真正读取 Library，证明新体系本身可独立工作。**
3. 旧 World/Lore 只作为历史兼容来源；用户有需要时再导入。
4. 不为了“架构完整”强迫用户经历一次大型迁移工程。
5. 不把清理历史技术债误当成新系统上线的前置条件。

因此，L4 应从“必须完成的迁移层”调整为：

> **可选的 Legacy Consolidation / Import 层。**

也就是：新系统不依赖 L4 才能成立；L4 负责帮助仍有旧资料的用户安全收口，而不是证明 Library 可用。

---

## 2. 新的阶段关系

建议将整体关系理解为：

```text
L1  Library 数据真源
        ↓
L2  可解释、受预算控制的读取
        ↓
L3  四模式真实消费 Library
        ↓
     ★ 新体系已经成立 ★
        │
        └── L4（可选）
             旧 World / Lore 盘点
                     ↓
                  dry-run
                     ↓
             用户决定是否导入
                     ↓
              安全导入 Library
```

**关键变化：L3 完成就是新 Library 产品闭环的主要终点。**

L4 不再承担“新架构必须完成的最后一块拼图”，而承担：

> “如果用户还有值得保留的旧 World/Lore，如何安全地把它们带进已经可用的新 Library。”

这能避免一种危险的工程惯性：

> 因为已经规划了 L4，所以无论用户是否需要，都继续实现 inventory、journal、rollback、入口退役等完整迁移平台。

---

## 3. L4 的新目标

### 3.1 第一目标：看清旧资料，而不是立即搬旧资料

L4 首先应该回答：

- 用户到底还有多少旧 World？
- 有多少作品 Lore？
- 哪些已经被新 Library 替代？
- 哪些仍包含新 Library 没有的重要内容？
- 哪些只是旧运行系统的技术残留？
- 哪些根本没有迁移价值？

因此第一交付应是**只读 inventory + comparison**。

输出重点不是“准备创建多少新条目”，而是：

```text
旧资料 A
├─ 12 个角色
├─ 4 个地点
├─ 3 条规则
├─ 其中 14 项 Library 已有近似/同源内容
├─ 5 项可能值得导入
└─ 0 项必须立即处理

建议：保留旧资料，不执行迁移
```

或者：

```text
旧资料 B
├─ Library 中没有对应内容
├─ 包含 8 个角色 + 22 个历史事件
└─ 建议生成导入预览
```

**不要默认“发现旧资料 = 应该迁移”。**

---

## 4. 把“迁移”改成“显式导入”

建议产品和代码语义尽量使用：

- `legacy import`
- `import preview`
- `import plan`
- `import receipt`

而不是让“migration”暗示系统必须自动把旧世界升级成新格式。

二者区别是：

### migration 思维

```text
旧系统
  ↓
必须升级
  ↓
新系统
```

### import 思维

```text
旧资料（保留）
  │
  ├── 用户不需要 → 什么也不做
  │
  └── 用户需要 → preview → 选择 → import
                              ↓
                           Library
```

这更符合当前产品方向，也更符合“用户资料不能自动处理”的既有安全边界。

内部包名 `librarymigration` 第一版**不必为了命名重构**；避免为了方向调整制造无价值 churn。可以先保留包名，在契约和 UI 上使用“旧资料导入/收口”语义。

---

## 5. 建议重新切分 L4

### L4.0 —— 先做“是否值得迁”的判断

这是原方案里缺少的一层。

只读统计旧 World/Lore，并与当前 Library 做**保守比较**。

注意：

- 第一版不要用 LLM 自动判断“这两个角色其实是同一个人”。
- 不做自动实体融合。
- 可以按稳定来源 ID、明确 binding、已知 source identity 做确定性匹配。
- 名字相同只能提示“可能重复”，不能自动认定相同。
- 比较结果只是帮助用户决定要不要继续。

验收标准：

> 在零写入情况下，用户能知道自己有没有值得导入的旧资料。

如果多数真实资料都已经没有迁移价值，L4 可以在这里自然结束。

---

### L4.1 —— Import Preview

只有用户选中某份旧资料后，才建立详细转换计划。

保留原方案好的部分：

- stable ID mapping；
- World/Lore → Library item 映射；
- timeline/event 转换；
- source identity/revision；
- conflict / omission / warning；
- dangling relation；
- 未知/null/缺失不猜；
- plan fingerprint。

但 preview 应允许用户：

- 排除某些条目；
- 只导入选定类别；
- 看到可能重复项；
- 看到无法可靠转换的字段；
- 直接取消。

**preview 仍然必须零写入。**

---

### L4.2 —— Explicit Import

只有明确确认 preview 后才执行。

保留现有方案中的安全要求：

- 输入 revision/fingerprint 在确认后变化 → confirmation 失效；
- 精确备份所选来源；
- hash/readability 校验；
- 原件不修改；
- 原子创建/写入；
- 相同 fingerprint 幂等；
- receipt 不存正文/Key/绝对路径；
- 失败不能报告成功；
- 不产生半完成 Library。

但建议第一版严格限制为：

> **一个旧来源 → 一个新 Library，或导入到一个明确选中的 Library。**

如果“导入已有 Library”会显著增加 CAS/冲突/回滚复杂度，则第一版只允许**创建新 Library**，不要为了完整性硬做 merge。

---

### L4.3 —— Verify + Archive Hint

导入成功后只做：

- 核对条目/关系/事件；
- 用 L2 验证可读；
- 如 L3 已完成，用目标模式做一次受控读取验收；
- 显示旧来源仍然存在；
- 给用户“以后可以不再使用旧入口”的提示。

**不要自动：**

- 删除旧 World/Lore；
- 隐藏旧入口；
- 修改旧存档；
- 把旧文件标记成已废弃并阻止打开；
- 清理磁盘目录。

旧入口退役应继续是独立的用户决定，不属于 import 成功的副作用。

---

## 6. 建议砍掉或延后的复杂度

以下内容除非真实用户数据证明需要，否则不要在 L4 第一版实现：

1. 多个旧 World 自动融合成一个 Library。
2. 自动把旧 Lore 与已有 Library 条目合并。
3. LLM/AI 自动判断重复实体。
4. AI 自动解决冲突。
5. 全盘扫描旧数据。
6. 自动批量迁移全部作品。
7. 自动删除旧目录。
8. 自动重写 Obsidian / knowledge graph。
9. 为迁移建立第二套长期 Registry。
10. 为迁移建立新的模型链/Agent。
11. 因为“以后可能需要”而先做复杂 migration journal 平台。
12. 把书籍、互动故事、Adventure save、Module4 localStorage 混进 Library 导入。

如果简单的原子写 + receipt + 可验证备份已经足以保证第一版恢复，不应提前建设通用事务框架。

---

## 7. 与 L3 的关系必须重新写清楚

后续 AI **不得因为 L4 未完成而阻塞 L3 产品闭环**。

正确依赖应是：

```text
L1 → L2 → L3
           │
           └── 产品已经可以使用新 Library

L4.0/L4.1 可在不写真实数据的前提下独立研究
L4.2+ 只有用户确实要导入旧资料时才继续
```

因此：

- L3 四模式验收通过后，可以宣布“新 Library 已成为可工作的作品设定来源”。
- 不能说“因为旧 World 还没迁，所以 Library 还没完成”。
- L4 的未完成状态应描述为“旧资料兼容/导入尚未完成”，而不是“新 Library 未完成”。

---

## 8. 关于“唯一真源”的修订解释

“Library 是作品设定唯一主要编辑真源”不等于：

> 磁盘上不能存在旧 World/Lore。

正确含义应是：

- 新创作不再要求同时维护 Library + World 两份设定；
- 四模式读取新作品背景时优先走明确选择的 Library；
- 旧 World/Lore 可以作为历史资料存在；
- 没有执行 import 时，不与 Library 双向同步；
- import 后也不建立双向同步；
- 用户仍可为了兼容旧功能保留旧入口。

目标是消除**双重编辑责任**，不是追求“物理上只剩一份文件”。

## 9. 对现有 C1–C5 清单的建议

正式改 checklist 前先由 AI1/用户确认。建议未来改成：

| 新任务 | 含义 |
| --- | --- |
| **C0 Legacy Inventory** | 只读列出旧资料及是否有明显导入价值 |
| **C1 Conservative Comparison** | 与 Library 做确定性/保守对照，不自动融合 |
| **C2 Import Preview** | 用户选择来源后生成零写入计划 |
| **C3 User Decision Gate** | 用户明确决定“导入 / 暂不导入” |
| **C4 Safe Import** | 仅在用户确认后备份、原子写、幂等、receipt |
| **C5 Verify / Optional Retirement** | 验证新库；旧入口退役另行决定 |

其中 **C0–C2 是可以主动建设的产品能力**。

**C3 以后是按需能力。**

如果用户看完 C0/C1 后决定：

> “这些旧东西我不要迁。”

那么这应该被视为一个**合法的 L4 完成结果**：

```text
Legacy review complete
Import requested: no
User data changed: no
New Library status: unaffected
```

而不是把项目永远挂在“L4 未完成”。

## 10. 后续 AI 的实施纪律

任何 AI 接手本文后：

1. **不要直接开始改代码。** 先核对当前 HEAD、工作树、最新正式 L4 契约与任务清单。
2. 本文是方向提案，不是用户对真实资料 apply 的授权。
3. 若决定采用本方向，先修改正式 L4 plan / blueprint / checklist，使文档一致，再实施。
4. 不要顺手重命名大量 `librarymigration` 包/文件；语义调整优先于代码搬家。
5. L4.0/L4.1 必须能用虚构 fixtures 完成。
6. 任何真实数据写入都必须再次经过具体来源 + preview + 用户确认。
7. 不因为“迁移工具已经写好了”就自动运行。
8. 不为了完成勾选表而诱导用户迁移不需要的数据。
9. 不把 L4 扩展成 Canon、世界模拟、知识图谱或 AI 数据治理项目。
10. 若发现旧资料规模很小，优先选择更简单的实现，而不是维护原计划的最大复杂度。

---

## 11. 建议的成功定义

L4 第一版真正成功，不是：

> “所有旧系统都被自动迁走了。”

而是：

> **用户能够看清旧资料；需要的内容可以安全、可预览、可撤销地导入 Library；不需要的内容可以原样留下；整个过程不会阻塞新 Library 和 L3 的正常使用。**

这也是本方向修订最重要的一句话：

> **L4 是帮助用户摆脱旧资料负担的工具，不应该自己成为新的工程负担。**

---

## 12. 当前建议的项目终点

在采用本方向后，作品设定库主线应有一个明确终点：

```text
L1 数据可靠
  ↓
L2 读取可靠
  ↓
L3 四模式真实使用
  ↓
★ 主产品闭环完成 ★

L4：
  有旧资料需要 → 可选导入
  没有需要       → 到此结束
```

除非用户另立新范围，后续 AI 不应从这里自动继续发明 L5/L6、全局 Canon、世界模拟、多 Library 自动融合或 AI 自动治理。
