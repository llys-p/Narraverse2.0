## 目标

让一个预置场景中玩家**实际持有**的物品，通过统一 Prepare → Commit 交给指定 NPC。P1 使用内部可注入的结构化 ActionIntent 做无模型联调，**不要宣称自由语言 Interpreter、真实 Laya、云端叙事已经接通**。玩家原文可进入 trace，但不由关键词或客户端数值决定物品转移。

## 要实现的最薄完整链

1. 复用既有 `_ACTOR_STATE`、版本/事件、State Transition 及 A 可用的多实体原子提交骨架；在当前基线上按需适配，不整包 cherry-pick。确定**单一**物品归属真源，不同时维护两个会分叉的可写 inventory/owner。场景初始化由服务端完成且与 Prepare 分离。
2. `prepare_structured`（或等价内部入口）读取服务端快照与所有被读实体的版本，验证主体/目标/物品、持有、可转交、同位置/可及性。只在副本上构造逐动作结果、Canonical Outcome 和 State Proposal，返回 `analysis_id` 与原版本；正式状态、归属、回合和历史均不变。目标为自己、目标不明、物品未持有时给明确失败/澄清，不凭空转移。
3. `commit` 只接受服务端候选引用和期望版本；锁内核对版本、规则/候选来源并重算。重算与预览不同时返回 409、使候选失效，要求重新 Prepare；不得静默提交不同结果。一次原子发布物品归属、涉及实体状态、正式历史、版本和回执，异常全回退。
4. 同一个 `event_id` 的重复提交返回原回执且 `replayed=true`，不再次转移/推进时钟；不同载荷复用事件 ID 冲突。下一轮快照读到新归属。旧路由若改动曾读取的角色状态，原候选须 stale。
5. 给 P2 留清楚的 `move` / `take` 扩展点，但**本轮不实现 P2 玩法、LLM、Laya、页面或 Narration**。未来硬前提要短路，不用有限难度惩罚代替拒绝。生产 HTTP 不开放注入难度、delta、Outcome 的口子。
