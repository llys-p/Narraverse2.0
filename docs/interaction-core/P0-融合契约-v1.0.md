## 1. 第一版究竟交付什么

玩家可以自由输入，系统理解其尝试、检查服务端事实、按规则得到可解释的行动结果，统一提交状态，再由云端模型自然演出这个结果。下一轮要读取真正提交过的结果。第一版先闭合一个小场景和有限动作，不扩完整 RPG、NPC 目标规划器、长期记忆或 Director。

借用 A 的状态/事务思路、B 的语义解析与提交重验、C 的分级结算和失败前进；**不直接合并整套候选**。A 未运行验证，B 最新复核为静态，C 的通过数字来自其交接，均不能代替融合版验收。D 核对 A `bdca76a`、B `4e61eca` 与当前 `a55ef9a`（增量仅文档）、C `b3a18f4`；结论来自静态源码复核，不冒充运行时攻击通过。

路径取舍：直接以 A 为底座，事务复用较快，但语义与叙事自由度要补；直接以 C 为底座，分级玩法已有形状，但硬前提和外来难度的边界需要修；直接以 B 为底座，自由输入较完整，但其演示状态/事务不能不经核对就替代现有协议。**选择共同基线上的薄融合**：只取经过契约适配的模块，先让一件物品转移贯通。D 的源码复核表明 A 的 `commit_interaction_bundle` 已给出多实体事务的可复用骨架；融合版以此作最小扩展，不新建第二套状态真源。

## 2. 唯一运行链与权威

```text
玩家原文 + 服务端会话快照
 → Interpreter：ActionIntent[]，含原文依据与歧义状态
 → Facts：核实资源、位置、归属、目标、可见事实
 → Laya：逐目标 Evidence / 辅助信号（可缺席）
 → Resolver：按动作顺序在快照副本上结算
 → Canonical Outcome + State Proposal（候选）
 → Commit：重验版本、规则、档案并原子发布
 → 权威回执 → Story Agent → 下轮读取回执后的状态
```

| 层 | 可以决定 | 不能决定 |
|---|---|---|
| Interpreter | 玩家尝试的动作、对象、目标、条件及引用的原话 | 世界事实、难度、成功档位、数值变化 |
| Facts / Rules | 当前事实、动作硬前提、服务端难度与资源约束 | 把玩家声明当已发生事实 |
| Laya | 经能力档案标注的信号、倾向、可写状态建议 | 物品归属、动作是否实际成功、直接落盘 |
| Resolver | 每个动作的成功程度、成本、后果、机会 | 直接修改正式状态 |
| Commit | 唯一写入 Actor / World Runtime、版本、正式历史与回执 | 接收客户端自报的 delta 或 outcome 当权威 |
| Story Agent | 已提交事实的语言、节奏、人物表达 | 重判成功失败、增删已发生的物品和状态变化 |

这里的 World Runtime 是会话运行态，不回写持久 World 定义；正式 Narraverse 存储适配留 P6。

## 3. 最小跨模块契约

以下约定**语义**，内部类名和序列化字段可由实现者调整，但跨模块交接需要一份版本化 schema。

- `TurnInput`：`session_id`、稳定的 `event_id`、`actor_id`、玩家原文、期望版本集合。生产 HTTP 不接受事实、难度、state delta 或成功档位；测试注入端口与生产输入分开。
- `ActionIntent`：动作类型、主体、目标、对象、顺序、可选依赖/条件、否定/假设/引用状态、原文片段。一个回合允许多个意图和目标；无法确定必需对象或目标时返回澄清，不暗选。`negated/hypothetical/quoted` 不作为真实物理尝试，也不计作行动失败；必要时可另生成交流行为。
- `FactCheckResult`：对每个动作的前提给出满足、阻止、未知或需澄清，附所用服务端事实来源。**阻止或资源不足的物理动作直接短路为未执行/失败，不进入 margin 公式**；可明确收取尝试成本，但不能产生被阻止的物理效果。表达声明可作为独立交流动作留下“某人声称”，不能生成“物品已交付”。
- `LayaEvidence`：目标角色、输入片段、信号、能力等级与 active/auxiliary 状态、翻译/模型来源。档案等级不伪装为单次 confidence；auxiliary 可供叙事参考，不进入可写 delta。
- `ActionResolution`：逐动作记录成功程度、实际效果、失败/跳过原因、消耗与规则贡献。后续动作读取前一步的**模拟结果**，不能重复花费资源。整体 `partial_success` 只是摘要，逐动作结果才是准绳。
- `CanonicalOutcome`：区分 `attempted`、`achieved`、正式事实/状态变化、cost、complication、opportunity 及可见性。Opportunity 表示下一步可尝试，不代表已发生。只有 Commit 回执中的 Outcome 是本轮权威。
- `Pending/CommitReceipt`：服务端保存候选，客户端仅提交 `analysis_id`、事件引用和期望版本；提交回执含 `commit_id`、新版本、实际变更、权威 Outcome。相同提交重试返回同一回执。

关系以 `(session_id, from_actor_id, to_actor_id)` 的有向身份表达。现有单向量只可在明确映射为 `NPC → 玩家` 时复用；没有成对关系数据的 NPC→NPC 社交状态改变返回 `UNSUPPORTED_RELATIONSHIP`，不得借用该 NPC 对玩家的值。NPC→NPC 物理行动仍可按自身资源与事实结算，不凭空加入关系修正。知识分角色可见和私有；声称、相信、观察到和客观成立是不同事实类型。第一版至少处理 2 NPC × 2 sessions 的隔离语义，不要求立即建完整关系矩阵。

## 4. Prepare / Commit 与失败语义

Analyze / Prepare 不得改变游戏状态、正式历史、回合时钟或物品归属，也不得初始化 Actor 状态桶。只允许进程内以 `(session_id, event_id)` 键控的 in-flight/Pending、TTL 和版本元数据；这些不是已提交事件或正式历史。语义不可解析、必须澄清、云端异常、所依赖的 Laya 不可用，均不能偷偷改成中性成功。规则能独立裁决的动作可显式 `rules_only`，其回执必须表明没有 Laya 证据。

Commit 在同一事务边界内重验所有被读取的实体版本、场景/规则版本、能力档案与候选结果；发布所有角色、世界运行态、资源、正式历史、版本和回执，任一失败全回退。**锁内重算与预览不一致时返回 409、候选失效，客户端须重新 Prepare；不得静默以新结果替换玩家预览。**旧路由对同一实体写入须让候选失效。过期、拒绝、旧版本和不同载荷重用 `event_id` 应明确失败；已提交的同一请求可幂等重放原回执。

叙事只读取提交回执。云端叙事超时或文本违约时，保留已提交结果并重试叙事，不重新提交。明显事实冲突需重试或回退到权威结果表达；单靠禁词表不能证明语义正确。

## 5. 首个可玩的最小范围

P1 用“玩家把自己持有的一件物品交给指定 NPC”做纵向切片：存在且持有 → 分析预览零写 → 确认 → 原归属失去、目标获得、下一轮可读；无物品、错目标、重复提交、网络重试有清楚结果。P2 扩成询问线索、`move` 到旧井、`take/pickup` 拾取钥匙、返回并 `unlock` 开门，以及一次分级对抗。`take` 的最低硬前提是物品在主体当前位置、当前无人持有且可拾取；归属变化只由规则结果经 Commit 写入，模型不能直接改 owner。首版动作集至少包括 communicate/question、transfer、inspect、move、take、unlock 与一个可分级对抗动作；其余动作可以继续限于 Demo。允许部分成功，但硬前提不可被关系值或语言模型绕过。人际交流与物理效果分开结算，物体处理不复用 NPC 攻击规则。
