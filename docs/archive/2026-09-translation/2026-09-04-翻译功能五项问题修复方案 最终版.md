- 阶段 7 复核补齐应用策略与队列边界：`master_review` 即使质量通过也保持 `pending_review`，进入总库集中人工确认；Master 待审任务不再进入顶部“全部采纳”，“前往总资料库处理”改为可点击跳转；Python 15/15、队列测试 9/9 复验通过；

- Vite 默认旧 `dist/assets` 清理由当前安全守卫拦截，使用全新 outDir 验证成功，3612 个模块完成转换；

- 正式构建已更新到 `denova-src/output/denova.exe`，服务在 `127.0.0.1:8080` 启动；翻译结果窗口加载 5617 条待处理展示项，选择全部候选后显示“批量确认应用（508）”且按钮可用。本次仅查看和选择，未点击应用，现有候选与用户数据未被改写；其他模块不在本轮验收范围内。

## 0. 最终结论

五项问题可以在现有架构内修复，不需要重写翻译系统，也不需要新建独立审核后台。

最终方案采用“机器负责筛选，人工负责最终判断”的方式：

1. 明确合格的译文自动进入总资料库；
2. 可疑译文和失败译文不自动生效，统一进入当前总库条目的“Denova 处理结果”；
3. 用户在一个窗口中查看原文、候选译文和异常原因，直接修改多个字段；
4. 支持批量重新翻译、批量保存修改、批量确认应用和部分失败继续；
5. 用户确认后生成正式翻译版本，再由用户显式同步到当前冒险；
6. 本地翻译队列只保留运行监控、暂停、刷新、重试和清理能力。

这会把“翻译是否正确”从容易误判的自动规则，降级为自动分流问题。自动规则只决定“可直接采用”还是“交给人看”，不替代人的内容判断。

## 1. 范围与不做事项

### 1.1 本期解决的五项问题

1. 模型没有产生可用中文译文；
2. 译文中英文混杂或大段回显英文原文；
3. 总资料库应用新译文后，已加入冒险的条目没有更新；
4. “Denova 精修”启动后缺少可靠反馈，用户看起来像按钮无效；
5. 本地翻译队列缺少明确刷新和批量清理能力。

### 1.2 本期明确不做

- 不重写 HY-MT 或 Denova Master 架构；
- 不新增 Module4 专属翻译、模型或 API 配置；
- 不让翻译器直接覆盖用户正在使用的冒险内容；
- 不把本地翻译队列扩建成第二套内容审核后台；
- 不自动重投影整个 import transaction；
- 不同步角色卡 opening presets；它们继续作为冒险实例的本地快照；
- 不为了本次修复引入新的浏览器自动化框架、数据库或后台服务。

当前系统已经具备大部分基础能力：

- `tools/denova_full_export.py` 已有 HY-MT 翻译、缓存、占位符保护、任务队列、重试和 8097 HTTP 接口；
- 翻译任务已经有 `completed / pending_review / failed / conflict / applied` 等状态；
- `MasterProposal` 已能保存字段级候选、风险、原因、输入版本和 CAS 校验信息；
- 总资料库详情页已经有“Denova 处理结果”、逐项应用和批量应用入口；
- 总资料库运行态已经能合并 Master 内容版本与 8097 队列状态；
- 本地翻译队列已经有单任务刷新、重试、删除和人工编辑的底层 API；
- Master 已记录当前冒险实例、目标 Lore ID 和 `LoadedRevision`。

因此本期主要工作是收紧质量契约、把异常结果接入现有 Proposal/处理结果视图、补齐批量交互，以及增加单资产手动重投影。

## 3. 最终数据流

```text
导入素材
  ↓
8097 / HY-MT 生成候选译文
  ↓
统一质量校验（缓存结果、首次结果、重试结果使用同一规则）
  ├─ pass           → 自动写入总资料库正式翻译版本
  ├─ needs_review   → 不生效，进入“Denova 处理结果”
  └─ failed         → 不生效，携带原文/原因/可用候选进入“Denova 处理结果”
                           ↓
                  人工集中编辑、批量确认
                           ↓
                  MasterProposal 校验与应用
                           ↓
                  总资料库正式翻译版本
                           ↓
                  用户点击“同步到当前冒险”
                           ↓
                  精确更新当前资产的冒险实例
```

任何 `needs_review` 或 `failed` 结果都不得被成功缓存、自动应用或自动同步到冒险。

## 4. 问题 1 + 2：无可用中文和中英文混杂

### 4.1 质量校验改成三态判定

新增统一的候选质量判定结果：

```text
pass          明确可用，可以自动采用
needs_review  有可用内容，但存在回显、混杂、占位符或结构疑点
failed        空响应、调用失败、结构损坏，或完全没有可用候选
```

判定结果至少携带：

- `quality_status`；
- `quality_codes`：机器可处理的问题码数组；
- `quality_reason`：面向用户的脱敏说明；
- `quality_contract_version`；
- 可用时保留 `candidate_translation`。

建议问题码保持稳定，例如：

- `empty_output`；
- `source_echo`；
- `mixed_language`；
- `missing_cjk`；
- `placeholder_mismatch`；
- `structure_mismatch`；
- `bridge_or_model_error`。

### 4.2 所有候选必须通过同一质量契约

以下四类结果不得各走一套宽松标准：

- 旧缓存命中；
- 第一次模型输出；
- 自动重试输出；
- 人工修改后准备应用的内容。

机器结果必须通过统一校验才能自动采用。人工修改结果仍执行占位符、结构和空值检查，但用户明确确认后，可以接受有意保留的外文专名；此时记录 `confirmed=true`，不得伪装成机器自动判定通过。

### 4.3 占位符和受保护内容

质量统计前先排除受保护片段，校验完成后再精确恢复：

- `{{user}}`、`{{char}}` 等模板变量；
- URL；
- 数字和版本号；
- 代码片段、明确标记为不可翻译的标识符；
- 术语表中要求保留的专名。

不能仅因为出现拉丁字母就认定翻译失败。检测目标是自然语言英文句子或原文回显，而不是变量、URL、缩写和角色名。

占位符要求：

- 数量一致；
- 名称一致；
- 不丢失、不新增、不改写；
- 恢复失败时不得自动应用。

### 4.4 英文回显与混杂判断

不采用单一“Latin 字符比例大于某个阈值”的粗略规则。应组合判断：

- 输出是否与英文原文完全或近似相同；
- 是否存在连续自然语言英文句段；
- 对本应翻译的英文内容，输出是否具有足够中文信息；
- 排除受保护片段后，英文词序列是否仍明显超出合理范围；
- 是否出现模型解释语、道歉语、前后缀或重复原文。

自动规则宁可把边界结果送人工，也不要为了提高自动通过率放进混杂译文。

### 4.5 Prompt、重试和候选选择

Prompt 明确要求：

- 只返回最终译文；
- 不解释、不复述原文、不增加标题；
- 使用简体中文；
- 原样保留受保护变量、URL、数字和指定专名；
- 保持输入文本的段落和必要结构。

自动重试最多一次：

1. 第一次结果为 `pass`：直接采用；
2. 第一次为 `needs_review` 或 `failed`：使用更明确的纠错 Prompt 重试一次；
3. 重试结果为 `pass`：采用重试结果；
4. 两次都未通过：不采用“中文更多的那个”作为成功结果；可以把较完整候选作为人工参考，但状态必须是 `needs_review` 或 `failed`。

### 4.6 版本与缓存

本次建议一次性升级：

```text
TRANSLATION_CACHE_VERSION     10 → 11
TRANSLATION_PROMPT_VERSION     6 → 8
TRANSLATION_VALIDATOR_VERSION  6 → 8
```

任务摘要必须同时包含：

- 原文及其 SHA-256；
- 翻译模式和目标语言；
- cache version；
- prompt version；
- validator/quality contract version。

缓存规则：

- 只有 `pass` 可以写入成功缓存；
- `needs_review`、`failed`、网络异常和空响应不写成功缓存；
- 读取缓存后仍按当前质量契约复验；
- 版本变化必须生成新的任务 ID，不能把旧任务误当成新版本已完成；
- 已经进入 Master 的历史坏译文不会因为升级缓存自动消失，必须提供“重新翻译所选字段”入口重新进入流程。

## 5. 人工判断集中到“Denova 处理结果”

### 5.1 界面位置

人工内容判断统一放在：

```text
叙界总资料库
  → 打开一个总库条目
  → 处理进度
  → Denova 处理结果
```

首期范围是“当前总资料库条目内的全部异常字段集中处理”。一个角色卡或设定书条目中的异常字段全部在同一个结果区展示，不再要求用户到本地翻译队列逐个打开任务窗口。

总库列表对存在待处理字段的资产显示数量徽标，方便用户定位；不新增跨资产的复杂审核后台。

### 5.2 每一行显示内容

每个待处理字段显示：

- 选择框；
- 字段中文名称和必要的字段路径；
- 原文；
- HY-MT/Denova 候选译文；
- 可直接编辑的译文输入区；
- 异常类型和简短原因；
- 风险等级；
- 状态：待修改、待确认、已应用、冲突、失败；
- 单项“重新翻译”“保存并应用”操作。

默认优先展示对用户有意义的字段名称；原始路径放在次要信息中，避免让新手依赖技术路径判断。

如果翻译完全失败，译文输入区允许为空并显示“请输入译文或重新翻译”；只有用户保存时才创建非空 Proposal。

### 5.3 与现有 Proposal 的关系

不新建第二套审核数据：

- `pending_review` 和 `failed` 的 8097 任务由 Master runtime 聚合为待处理行；
- 有候选且用户准备采用/修改时，创建 `kind=recovery`、`apply_mode=confirm` 的 `MasterProposal`；
- Denova 精修仍创建 `kind=polish` Proposal；
- 人工修改保存前执行结构校验，应用时继续走现有 CAS；
- Proposal 记录原文、当前译文、用户修改、原因、风险、输入 revision、source hash 和 base translation version；
- CAS 冲突不得覆盖新版本，冲突行保留在结果窗口并提示重新读取。

### 5.4 批量操作（本期必做）

结果区必须提供以下批量能力：

#### 批量选择

- 全选当前筛选结果；
- 选择全部“需要人工处理”；
- 选择全部失败项；
- 取消全选；
- 已应用项默认不参与选择。

#### 批量重新翻译

- 对所选 `pending_review / failed / conflict` 字段逐项调用现有 retry 能力；
- 显示 `已处理 / 总数 / 成功 / 失败`；
- 单项失败不能中断剩余项目；
- 防止同一任务重复提交；
- 完成后只刷新当前资产运行态和处理结果。

#### 批量保存人工修改

- 用户可连续修改多行，最后一次点击“保存所选修改”；
- 对每个有改动且非空的字段创建并验证 Proposal；
- 未修改、仍为空或结构校验失败的行不应用，并在原行显示原因；
- 已成功保存的行进入“待确认”状态；
- 离开页面前若有未保存修改，应给出轻量提示。

#### 批量确认应用

- 对所选已验证 Proposal 一次提交批量应用；
- 每个 Proposal 独立执行 CAS 和应用，某一项失败不得回滚已经成功的其它独立字段，也不得阻断后续字段；
- 返回逐项结果和汇总：应用数、冲突数、失败数、跳过数；
- 成功行立即显示新的 translation version；
- 冲突/失败行保留用户编辑内容，便于重新读取后再处理。

高风险字段也允许在同一窗口批量编辑，但批量应用前必须显示一份合并确认清单，并要求用户明确确认“应用所选高风险字段”。后端请求必须携带显式高风险确认标记；未确认时只返回逐项 `requires_high_risk_confirmation`，不能静默跳过或自动采用。

#### 批量操作反馈

所有批量操作统一使用结构化结果：

```json
{
  "total": 4,
  "succeeded": 2,
  "failed": 1,
  "conflicted": 1,
  "results": [
    { "id": "...", "status": "applied" },
    { "id": "...", "status": "failed", "error": "脱敏后的原因" }
  ]
}
```

错误文本不得包含 API Key、Authorization、完整请求体或完整用户存档。

## 6. 问题 3：应用译文后手动同步到当前冒险

### 6.1 最终接口粒度

重投影必须以单个 Master 资产为单位：

```go
ReprojectMasterAsset(masterItemID string)
```

不能使用 `ReprojectMasterImport(importID)`，因为一个 import 可能包含多个 Master 资产；同步整个 import 会误更新用户没有选择的其它资产。

当前冒险实例的查找、workspace/adventure key 计算和目标完整性检查必须放在 `book.Service` 内部。API Handler 只负责读取 `masterItemID`、调用服务和返回结果，不能调用包内私有的 `masterHashString`。

### 6.2 同步前置条件

后端必须确认：

- 当前 workspace 是目标冒险；
- 当前 Master 资产在这个冒险中有且只有一个有效 instance；
- instance 的 `TargetLoreIDs` 和嵌套条目映射完整；
- 每个目标 LoreItem 仍然存在；
- 当前 Master revision 与已加载 revision 的关系明确。

找不到实例、出现重复实例、目标缺失或映射不完整时必须失败并说明原因。不能 `continue` 后仍更新 `LoadedRevision`，否则界面会产生“同步成功但内容没更新”的假状态。

### 6.3 更新边界

更新操作从现有冒险目标条目复制完整对象，再覆盖 Master 拥有的内容字段，避免稀疏 Update 把本地状态清空。

由 Master 更新：

- 展示名称（通过名称冲突检查后）；
- 简介/正文；
- 关键词和次级关键词；
- 与源内容版本相关的字段。

必须保留冒险本地字段：

- ID；
- `Enabled`；
- load mode；
- 本地图片/封面；
- 冒险运行态与本地开关；
- 本地实例 provenance/绑定身份；
- 不属于 Master 所有权的本地扩展字段。

名称分配前先从冲突集合中排除本次资产自己的全部 target ID，避免原名被误判占用而生成 `Alice-2` 一类伪冲突。

Opening presets 本期不参与同步，继续保留冒险实例创建时的本地快照。

### 6.4 原子性与 LoadedRevision

重投影按一个资产事务处理：

1. 验证全部目标和映射；
2. 生成全部 update operations；
3. 保存必要文件快照；
4. 应用 LoreItem 更新；
5. 全部成功后更新 instance 的 `LoadedRevision`；
6. 任一步失败则恢复本次已改文件，并保持旧 `LoadedRevision`。

绝不能在部分目标失败时把整个资产标记为已同步。

### 6.5 API 与前端

新增：

```text
POST /api/library/assets/:id/sync-adventure
```

返回当前资产的同步结果、更新 ID、旧/新 revision 和逐项状态。

总库详情页在“加入冒险”旁提供“同步到当前冒险”：

- 是否可以同步由后端返回的当前冒险 usage 决定，不能只依赖前端 `usages.length > 0`；
- 仅在已加入当前冒险且有新版时启用；
- 用户不点击则冒险实例不变化；
- 批量确认多个译文后，只需对当前 Master 资产同步一次；
- 成功后刷新总库详情并触发 `nova:lore-updated`。

## 7. 问题 4：Denova 精修可靠反馈

### 7.1 轮询完成条件

启动精修前先记录当前资产已有 Proposal ID 集合，然后调用 Master Agent。

轮询只接受同时满足以下条件的新 Proposal：

- `proposal_id` 不在启动前集合中；
- `field_path` 与当前字段一致；
- `kind == polish`；
- 状态为 `candidate_ready` 或 `validated`。

不能主要依赖浏览器时间戳匹配，因为客户端与服务端时钟可能不一致，旧 Proposal 也可能被误认为新结果。

`conflict` 或 `rejected` 立即显示失败；达到超时则显示“任务仍未产生候选，可稍后刷新或重试”。

### 7.2 状态和生命周期

- 精修 loading 保持字段行局部状态，不提升成整个页面全局忙碌；
- 同一字段运行期间禁用重复点击；
- 建议每 3 秒轮询一次，上限 120 秒；
- 切换 Master 资产或卸载组件时清理 timer；
- 请求晚返回时不得更新已经切换的条目；
- 候选出现后自动刷新“Denova 处理结果”；
- 精修候选允许继续人工修改，并可参加批量保存和批量确认。

## 8. 问题 5：本地翻译队列定位与操作

### 8.1 队列职责

本地翻译队列保留：

- 当前运行任务；
- 排队数量；
- 暂停/继续；
- 手动刷新；
- 失败任务重试；
- 取消任务；
- 清理失败任务；
- 跳转到对应总资料库条目。

对于 `master_auto / master_review` 任务，移除队列中的“全部采纳”和逐任务内容编辑入口，改为“前往总资料库处理”。这样不会在本地队列和总资料库形成两套互相竞争的人工确认路径。

如果仍有非 Master 的旧 Lore 翻译任务，可暂时保留原有编辑行为；它不属于本次总资料库审核迁移范围。

### 8.2 手动刷新

虽然页面已有约 1.2 秒自动轮询，仍保留明确的“刷新”按钮，便于用户排障和确认桥接服务状态。按钮调用现有 `getTranslationQueue()`，不新增后端接口。

### 8.3 批量清理失败任务

“清空失败任务”处理：

- `failed`；
- `conflict`；
- `cancelled`。

继续复用现有单任务 delete 端点，串行或小并发执行即可。每一项使用独立 `try/catch`：

- 某一项删除失败时继续处理其余任务；
- 显示 `已处理 / 总数 / 成功 / 失败`；
- 最后刷新队列；
- 删除保持现有软删除语义，审计记录不物理清除。

## 11. 实施顺序

1. **质量契约与版本**：先完成 Python 三态校验、统一候选验证、版本摘要和缓存规则；
2. **运行态接线**：让 Go Master runtime 读取质量状态和候选，形成总库待处理行；
3. **集中人工处理**：在现有“Denova 处理结果”中完成编辑、批量重译、批量保存和批量确认；
4. **单资产同步**：实现 `ReprojectMasterAsset`、API 和“同步到当前冒险”；
5. **精修反馈**：按新 Proposal ID 轮询，接入同一个处理结果区；
6. **队列收束**：增加刷新/批量清理，Master 内容审核改为跳转总资料库；
7. **构建和实际运行验收**：依次完成 Python、Go、前端测试以及正式 executable smoke test。

该顺序保证每一步都有独立可验证结果，也避免先做 UI 后发现底层状态无法表达。

## 12. 测试门槛

### 12.1 Python

## 13. 最终人工验收路径

1. 导入一份同时包含英文正文、占位符、URL、专名和多个字段的测试素材；
2. 确认明确合格字段自动进入总资料库；
3. 确认英文回显、混杂和失败字段没有自动生效；
4. 打开该总库条目的“Denova 处理结果”，一次看到所有异常字段；
5. 同时修改至少两个字段，另选一个字段执行批量重新翻译；
6. 执行批量保存和批量确认，确认成功项生效、故意制造的冲突项保留；
7. 对一个字段执行 Denova 精修，确认候选自动出现在同一结果窗口；
8. 将资产加入冒险，之后再修改总库译文；确认冒险不会自动变化；
9. 点击“同步到当前冒险”，确认只更新当前 Master 资产的对应实例，本地开关和运行字段不丢失；
10. 打开本地翻译队列，确认可以刷新、重试和批量清理，但 Master 内容判断入口指向总资料库；
11. 刷新页面并重启正式 executable，确认总库翻译版本、Proposal 状态和冒险实例保持一致。

## 14. 完成标准

只有以下条件同时满足才算完成：

- 合格翻译可以自动采用；
- 可疑/失败翻译不会自动生效或进入成功缓存；
- 人工可在一个总库“Denova 处理结果”窗口修改全部异常字段；
- 批量重译、批量保存、批量确认和部分失败继续均已验证；
- Denova 精修结果可靠出现于同一窗口；
- 总库译文可以由用户显式、精确地同步到当前冒险；
- 同步失败不会产生错误的 `LoadedRevision`；
- 本地队列只承担技术控制，不再要求用户逐个窗口判断 Master 内容；
- 定向测试、前端构建、Go 构建和正式 executable smoke test 均有真实结果；
- 未泄露 API Key、Authorization 或完整用户存档；
- 实施中若修改源码或配置，已按项目规则更新协作日志。
