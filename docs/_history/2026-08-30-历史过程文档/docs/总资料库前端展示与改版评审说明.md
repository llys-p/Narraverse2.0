# Narraverse / Denova 总资料库前端展示与改版评审说明

> 用途：提供给参与产品设计的其他 AI，帮助其理解总资料库目前的前端形态、用户目标与体验问题，并提出改版方案。
>
> 本文只讨论用户看到的页面、信息层级、操作流程和中文文案，不讨论代码、接口或后台实现。

## 一、产品定位

总资料库是 Denova 中独立的“可复用资产中心”。

它不是一本普通书籍，也不是某个冒险内部的资料列表。它负责集中保存经过整理和翻译的角色卡、世界设定和 Lorebook，让用户以后创建不同冒险时可以直接使用，不必反复上传、清洗和翻译同一份文件。

正式资产粒度是：

```text
一张角色卡 / 一个独立设定文件
=
一个用户可见的总库资产
```

例如总资料库应该显示：

```text
艾可
凯特
《苏斯魔法书》
《赛博朋克2077》世界信息
仙侠
```

而不应该把角色卡或设定书内部的几十个小条目全部拆到总库列表中。

内部小条目仍然存在，也可以分别翻译和处理，但它们属于整张卡或整本设定书的内部内容。

## 二、主要用户和核心任务

当前主要用户是个人本地使用者，技术背景不是页面设计的前提。用户进入总资料库时，主要想完成以下事情：

1. 看看自己已经保存了哪些角色卡和设定书；
2. 快速判断一项资产是否已经整理完成、能否使用；
3. 打开一项资产，阅读整张角色卡或整本设定书；
4. 了解翻译进行到哪里，是否真的需要自己处理；
5. 把已经可用的资产加入当前冒险；
6. 确认同一资产不会被重复加入；
7. 出现问题时，让 Denova 尽量自行恢复，只把真正需要决定的事情交给用户。

用户并不希望在日常浏览时理解资产 ID、哈希值、内部版本号、文件归档路径或后台任务错误。

## 三、当前总资料库前端

### 1. 入口

Denova 左侧主菜单中有独立入口：

```text
总资料库
```

进入后显示总库资产列表，不需要先进入某一本总库书籍。

### 2. 资产列表页

当前列表页提供：

- 搜索资产名称或来源文件；
- 按“角色设定卡 / 设定书”筛选；
- 按“角色 / 设定书”内容类型筛选；
- 按“待处理 / 可用”筛选；
- 分页；
- 查看中文资产名称；
- 查看来源文件；
- 查看当前状态；
- 查看已经被多少个冒险使用；
- 点击资产进入详情页；
- 通过“导入到总资料库”添加新资产。

目前真实总库中已有 9 个顶层资产，列表展示的名称包括：

- 艾可；
- 凯特；
- 罗克西；
- 北川真里；
- 异世界；
- 《苏斯魔法书》；
- 《赛博朋克2077》世界信息；
- 极限突破者；
- 仙侠。

这些资产目前均显示为“可用”。

### 3. 资产详情页

点击资产后，目前详情页集中展示：

- 资产中文名称；
- 资产类型与内容类型；
- 当前可用状态；
- 来源文件；
- 导入时间与文件大小；
- 完整角色卡或设定书内容；
- 七节点流水线；
- 字段翻译进度；
- 翻译版本；
- 已加入的冒险；
- “加入当前冒险”操作；
- 大量身份、版本和归档信息。

当前页面功能基本齐全，但所有信息被纵向堆在同一个长页面中，重要信息、阅读内容和诊断信息的视觉层级接近。

### 4. 完整内容

角色卡可以包含：

- 角色名称；
- 角色描述；
- 性格；
- 场景；
- 开场白；
- 示例对白；
- 角色规则与指令；
- 内部 Worldbook 条目。

独立设定书可以包含：

- 设定书名称；
- 多个内部设定条目；
- 每个条目的标题、正文和关键词；
- 条目的运行与触发说明。

当前详情页能够看到这些内容，但大设定书的条目很多时，浏览距离较长，缺少目录、搜索、分组和阅读聚焦。

### 5. 七节点流水线

当前显示：

```text
1 原件
2 解析
3 规范化
4 翻译
5 检查
6 可用
7 加入冒险
```

用户可见状态主要使用：

```text
等待
处理中
完成
警告
需要确认
```

其中“可用”是资产是否能加入冒险的真正完成状态；“加入冒险”只是展示该资产已经在哪些冒险中使用，并不是只能完成一次的单值状态。

### 6. 加入冒险

资产达到“可用”后，详情页提供：

```text
加入当前冒险
```

一张角色卡或一本设定书加入冒险时，可以在冒险内部展开成角色资料和多个 Lore 条目。同一资产重复加入同一冒险时不会再次生成重复内容。

“导入到总资料库”和“加入当前冒险”是两个不同操作：

```text
导入到总资料库
→ 只保存到总库

加入当前冒险
→ 才在冒险中生成可运行内容
```

前端文案必须持续清楚地区分这两件事。

## 四、当前最明显的 UI 问题

### 1. 技术信息像乱码

当前详情页会直接展示类似内容：

```text
总库资产 ID
一长串字符

当前版本
一长串 SHA

原件版本
另一长串 SHA

归档状态
一整段内部文件路径
```

这些信息对系统诊断有价值，但普通用户无法据此做出操作决定。它们占据详情页靠前位置，会让用户误以为总库损坏或数据出现乱码。

用户真正想看到的是：

```text
名称：《苏斯魔法书》
类型：设定书
状态：可用
来源文件：邪术召唤咒典.json
导入时间：2026年8月29日 16:37
文件大小：10.9 KB
已加入冒险：0
```

资产 ID、哈希值、内部版本号和完整归档路径应进入默认折叠的“技术信息”区域，并提供复制能力，而不是成为主要内容。

### 2. “来源”重复且表达不自然

当前页面可能连续出现多个“来源”，用户难以判断它们分别代表文件名、原件版本还是归档位置。

更自然的表达可以是：

```text
来源文件：邪术召唤咒典.json
原件状态：已安全归档
导入时间：2026年8月29日 16:37
```

### 3. “当前版本”不应直接显示为哈希值

用户看到“当前版本”时，通常期待：

```text
第 3 版
今天 16:37 更新
机器初译版本
```

而不是一长串校验字符。即使产品暂时没有友好的版本序号，也应该优先用日期、版本类型或“当前译文”表达，并将校验值放入技术信息。

### 4. 详情页过长

基本信息、完整内容、流水线、逐字段翻译、翻译版本和冒险使用情况全部纵向排列。资产内容较大时，用户很难知道自己当前处于哪个区域，也难以快速返回资产顶部或定位某个设定条目。

### 5. 资产已经“可用”，但仍显示大量未完成字段

内部可选条目可能仍在翻译或处理，但不会阻止整张资产使用。这会出现：

```text
资产状态：可用
翻译节点：仍有部分未完成
```

这个逻辑本身合理，但当前界面容易让用户感觉互相矛盾。

页面应明确区分：

```text
核心内容已完成，可以使用
部分辅助内容仍在后台完善
```

可选问题不应使用与阻断问题相同的警示强度。

### 6. 翻译版本信息过于密集

当前可能一次展示很多版本标识、字段路径和模型名称。普通用户更关心：

- 当前使用的是机器初译还是精修译文；
- 是否有待采用的润色候选；
- 是否有内容需要自己确认；
- 是否可以恢复旧版本。

长版本标识和逐字段历史应放入高级查看区域。

### 7. 内部条目缺少适合阅读的导航

大 Lorebook 可能有几十或几百个条目。当前逐条向下展开会带来：

- 页面太长；
- 难以找到某个条目；
- 无法只看未翻译或需要确认的条目；
- 条目正文、关键词和状态混在一起。

## 五、希望达到的 UI 体验

总资料库首页应该让用户在几秒内回答：

```text
我有哪些资产？
哪些可以使用？
哪些还在处理？
哪些真正需要我决定？
```

资产详情页应该让用户轻松回答：

```text
这是什么？
里面有什么？
现在能不能加入冒险？
还有没有必须由我处理的问题？
已经加入过哪些冒险？
```

整体体验原则：

1. 用户信息优先，技术信息后置；
2. 阅读内容、处理状态和版本诊断分层；
3. 默认只显示用户能理解、能行动的信息；
4. 系统可自行处理的问题不打扰用户；
5. 页面首先服务于“找资产、看内容、加入冒险”；
6. 大资产需要目录、搜索、折叠和定位能力；
7. 中文文案应自然，不直接展示英文内部状态词；
8. 保留 Denova 现有视觉语言，不做成完全不同的另一套产品。

## 六、建议其他 AI 重点考虑的页面结构

下面只是建议方向，不是必须照搬的最终答案。

### 1. 列表页

可以考虑让每个资产行或资产卡优先展示：

```text
中文名称
角色设定卡 / 设定书
可用 / 处理中 / 需要确认
来源文件
内部条目数量
已加入几个冒险
```

弱化当前版本哈希，突出资产封面、类型、状态和使用情况。

### 2. 详情页顶部摘要

顶部只展示最关键内容：

```text
资产中文名称
资产类型
可用状态
一句话处理摘要
[加入当前冒险]
```

例如：

```text
《苏斯魔法书》
设定书 · 8 个内部条目

核心内容已完成，可以加入冒险
部分辅助关键词仍在后台完善

[加入当前冒险]
```

### 3. 详情页内容分区

可以评估使用页签或左侧目录，例如：

```text
概览
完整内容
处理进度
翻译与版本
已加入冒险
技术信息
```

其中“技术信息”默认折叠或放在最后。

### 4. 完整内容阅读器

角色卡和设定书可以使用不同的阅读布局。

角色卡建议按语义分组：

```text
角色概览
性格与背景
场景与开场
示例对白
内部设定
高级指令
```

设定书建议提供：

```text
条目目录
条目搜索
分类或关键词筛选
只看需要确认
逐条折叠展开
当前条目阅读区
```

### 5. 流水线展示

七节点可以保留，但默认应该更像进度概览，而不是开发调试面板。

推荐表达：

```text
原件已保存
内容已识别
内容已整理
核心翻译完成
检查通过，有少量提醒
可以使用
尚未加入当前冒险
```

只有点击某个节点后，才显示更具体的字段情况。

### 6. 加入冒险确认

加入前可以提供简洁确认：

```text
将《苏斯魔法书》加入“大牛的武侠冒险”

将生成：
8 个设定条目

已存在的内容不会重复创建。

[取消] [确认加入]
```

成功后显示：

```text
已加入当前冒险
生成 8 个设定条目
```

## 七、必须保留的产品规则

无论 UI 如何改版，都需要保留以下规则：

1. 一张角色卡或一份设定文件只显示为一个顶层资产；
2. 内部条目不进入总库顶层列表；
3. 顶层资产名称必须优先显示中文译名；
4. 顶层名称尚未完成时，应明确显示“待翻译 + 原名称”；
5. “导入到总资料库”不能自动加入当前冒险；
6. 只有“加入当前冒险”才生成冒险内容；
7. 同一资产重复加入同一冒险不能产生重复内容；
8. 核心必需内容未完成时，资产不能显示为可用；
9. 单个可选内部条目失败不能让整张资产永久不可用；
10. 技术诊断信息可以隐藏，但不能从系统中消失；
11. 普通用户只处理真正需要决定的问题；
12. 当前阶段不要求设计资产自动同步、批量加入或内部条目级选择器。

## 八、希望其他 AI 提供的评审结果

请基于以上现状，重点从 UI/UX 而不是技术架构角度提出建议，并输出：

1. 对当前页面问题的优先级判断；
2. 推荐的信息架构；
3. 列表页的推荐布局；
4. 角色卡详情页的推荐布局；
5. Lorebook 详情页的推荐布局；
6. 七节点流水线应该如何简化；
7. 技术信息应该放在哪里、如何展开；
8. “加入当前冒险”的推荐交互；
9. 桌面端与窄屏窗口的适配建议；
10. 关键页面的文字版线框图；
11. 推荐中文文案；
12. 按 P0 / P1 / P2 排列的改版清单。

请避免：

- 重新讨论后台架构；
- 展开数据库、接口或代码实现；
- 建议把内部小条目重新变成顶层资产；
- 为普通用户展示更多技术错误；
- 一次加入大量与当前问题无关的新功能；
- 为了视觉效果破坏 Denova 现有整体风格。

## 九、改版验收标准

改版后的页面至少应该做到：

- 用户不再把 ID、SHA 和路径误认为乱码或故障；
- 用户进入列表后能迅速找到角色卡或设定书；
- 用户打开资产后能先看到名称、类型、状态和是否可加入；
- 用户可以方便阅读整张卡或整本设定书；
- 大设定书不需要依靠无限向下滚动查找条目；
- “可用但仍有辅助内容处理中”能够被自然解释；
- 技术信息仍可在需要时找到和复制；
- “导入总库”和“加入冒险”不会被误解成同一个操作；
- 页面没有直接暴露 `usable`、`staging` 等英文内部词汇；
- 用户只在真正需要确认时看到醒目的处理提示。

最终希望形成的体验是：

```text
总库列表简洁可浏览
→ 详情首先适合阅读
→ 处理进度容易理解
→ 技术信息默认隐藏
→ 一键加入当前冒险
```
