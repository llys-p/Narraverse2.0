# 《现有游戏项目分析报告》

> 项目：叙界 Narraverse × Denova  
> 审查日期：2026-08-15  
> 审查方式：静态阅读源码、运行数据目录、项目文档与协作日志；本轮未执行测试。  
> 标签约定：**【已确认】**源码或当前文件可直接证明；**【推测】**由现状推断；**【待确认】**当前本地资料无法证明；**【建议】**改进方向。

## 0. 结论先行

**【已确认】当前项目不是一款已经统一数据与规则的单体游戏，而是一个本地 AI 叙事创作/游玩平台。** Denova 是唯一顶层宿主，提供“写作 / 游戏 / 叙界”三个同级模式；其中与游戏直接相关的运行逻辑有三套：

1. **叙界在线 AI 冒险**：自由输入或选择行动，LLM 同时生成叙事和结构化状态变化。
2. **Denova 游戏模式**：Game Agent 生成叙事与状态提案，Go 后端校验状态、执行 d20 规则、原子提交事件日志。
3. **叙界离线小说游戏**：固定内容包驱动的本地事件图、检定、战斗与多结局；AI 只负责润色文字。

**【已确认】三者目前共享入口，但不共享统一的游戏状态真源。** 叙界与 Denova 的新数据同步只覆盖标题、设定、摘要、角色/设定素材和小说章节，不同步在线对话回合、战斗、任务、分支、快照或 Denova Interactive 的 Turn/StateDelta。

## 2. 当前核心玩法

### 2.1 叙界在线 AI 冒险（当前品牌主体验）

**【已确认】玩家实际流程：**

进入 Denova → 切到“叙界” → 配置 OpenAI 兼容 API → 创建新冒险 → 选择角色卡/世界设定卡、主题、模式、姓名和职业 → 可填写故事偏好 → AI 生成三套带标题的故事背景 → 玩家选择并编辑标题/世界/身份/职业/地点/目标/开场 → 开始冒险 → 阅读 AI 叙事 → 点击 AI 选项或自由输入 → 状态、任务、NPC、剧情线和战斗面板变化 → 自动保存 → 下一轮。

**【已确认】在线模式分为：**

- `adventure`：显示 HP/MP、属性、技能、背包、任务与战斗。
- `tavern`：偏对话和关系，默认弱化数值战斗。

### 2.2 Denova 游戏模式

**【已确认】玩家创建互动故事，选择讲述者、导演、规则模块、Actor State 模块、开场方式、回复长度与选项数量。** 每轮玩家输入行为；Game Agent 可读取 lore 和历史 Turn，必要时请求固定 d20 检定，输出正文后通过 `submit_interactive_turn` 提交状态变化与下一步建议。后端校验成功后，正文、StateDelta、规则结果和选择一起落盘。

### 2.3 叙界离线小说游戏

**【已确认】当前只有一个内容包《诸天轮回》：**4 个天赋、3 个金手指、4 个阶段、14 个主事件、6 个随机事件、4 个结局。玩家选天赋后获得随机属性与随机金手指，在事件中选择行动，进行本地 d20 检定和固定回合战斗，最终进入结局。

## 3. 核心游戏循环

### 3.1 叙界在线循环

玩家输入/选择行动  
→ 前端把当前角色、任务、NPC、剧情线、卡片、设定与上下文摘要重建为 System Prompt  
→ LLM 生成 `[NARRATIVE] / [STATE] / [CHANGES] / [CHOICES] / [QUESTS] / [COMBAT] / [CHARACTERS] / [PLOT]`  
→ 前端解析结构块  
→ 修改角色、任务、关系、NPC 图鉴、战斗与剧情节点  
→ 保存 IndexedDB、创建必要快照并调度 Denova 素材同步  
→ 渲染叙事与下一轮选择。

### 3.2 Denova 游戏循环

玩家输入行动  
→ 后端组装当前 Snapshot、Actor State、Lore、历史 Turn 与 Director 计划  
→ Game Agent 检索资料/历史  
→ 如有风险，后端执行固定 d20 规则并返回 RuleResolution  
→ Agent 输出正文并提交 schema-bound `state_changes + choices`  
→ 后端独立校验两个模块  
→ 编译 StateDelta、原子写入 JSONL Turn 事件  
→ 从事件路径重放当前状态  
→ 前端显示正文、状态账本与选择。

### 3.3 离线循环

本地事件节点  
→ 玩家选择  
→ 本地 RNG / d20 / 效果表判定  
→ 修改 HP、MP、金钱、属性、物品、旗标和金手指经验  
→ 进入结果页、战斗、随机事件、下一节点或结局。

## 5. 游戏状态与数据模型

### 5.1 叙界在线 Adventure

**【已确认】Adventure 是在线玩法的聚合根对象：**

- 身份：`id/title/theme/setting/mode/createdAt/updatedAt`
- 玩家：`name/profession/hp/maxHp/mp/maxMp/location/chapter/mood/level/exp/maxExp`
- 成长：`attributes/attributePoints/skills/skillPoints`
- 物品：`character.items`
- 对话记忆：`conversationHistory/contextSummary/contextCompressed`
- 剧情：`plotNodes/eventNodes/plotLines/currentLineId/aiIntro`
- NPC：`characterCards/mandalaCards/affections/relations`
- 任务与战斗：`quests/combat`
- 回溯：`snapshots/branches/versionLedger`
- 导演：`director`
- 小说：`novelPlan/novelChapters`
- 同步：`syncMeta`
- 统计：`stats.turns/deaths/startedAt`

**【已确认】浏览器持久化只序列化 `adventures/apiConfig/currentId/customThemes`。** `userProfile/currentPresetId/deletedThemes` 不在持久化 JSON 中；其中 Profile 只能靠手动导出/导入恢复。

### 5.2 Denova Interactive Story

**【已确认】Denova 采用事件溯源：**

- `StoryMeta`：故事 ID、标题、origin、Teller、Director、运行策略、开场、图片设置、冻结状态 schema、当前分支。
- `TurnEvent`：父事件、分支、玩家输入、正文、思考、工具展示、RuleResolution、TurnResult、TerminalOutcome、StateDelta、版本。
- `StateDelta`：通用 `StateOp` 与字段级 `ActorStateOp`。
- `Snapshot`：当前路径的 Turns、重放后的 State、Actor Schema、StoryGraph、压缩检查点。
- 初始状态根：`actors/actor_archives/scene/inventory/resources/world_flags/rules/threads/events/on_stage`。
- 默认 Actor：`protagonist`、`story`、`world`；可再创建重要角色和对手。

**【已确认】Turn 是历史事实真源，Actor State 是当前投影，Director 文档是未来计划，Lore 是稳定设定。** 这是当前项目里边界最清晰的一套状态架构。

### 5.3 离线游戏 State

**【已确认】离线状态 `S` 保存：**内容包、seed、属性、HP/MP、金钱、物品、天赋、金手指及等级经验、阶段与位置、flags、日志、历史、回合数、结局、待继续节点、复活使用情况与战斗状态。它只存在内存中。

## 6. 系统关系图（文字版）

### 6.1 在线叙界一次玩家操作

玩家动作  
→ `sendMessage()` 写入对话历史  
→ `buildSystemPrompt()` 读取玩家/NPC/任务/战斗/剧情/lore  
→ `manageContext()` 必要时压缩旧历史  
→ `callLLM()` 请求模型  
→ `parseGameResponse()` 将文本协议转为结构数据  
→ `applyParsedResult()` 修改权威 Adventure  
→ `applyCharacterUpdates()` 修改 NPC 记忆  
→ 记录 plot/event/snapshot/stats  
→ `saveState()` 写 IndexedDB并调度同步  
→ UI 全量刷新。

### 6.2 Denova 一次玩家操作

玩家动作  
→ API 创建/恢复互动任务  
→ Agent 获取 Snapshot + Actor Schema + Lore + Director  
→ 可调用 `search_story_history/read_lore_items/prepare_interactive_turn`  
→ 后端执行并记录 RuleResolution  
→ Agent 输出正文、调用 `submit_interactive_turn`  
→ 后端对状态与 choices 分模块校验  
→ `AppendTurnWithState()` 检查父版本、终局、schema 和状态操作  
→ Turn + StateDelta 原子写 JSONL  
→ Snapshot 通过重放事件生成  
→ 前端合并持久回合。

### 6.3 叙界与 Denova 的当前同步

叙界新 Adventure 保存  
→ 1.2 秒防抖构造精简 payload  
→ Python 8097 Bridge  
→ 写 Denova 工程 `setting/`、`chapters/`、`.denova/lore/items.json`  
→ Denova 修改这些受管文件  
→ 用户返回叙界时拉回设定、章节和 lore  
→ 更新 Adventure。

**【已确认】该链路没有连接 Denova Interactive 的 Story/Turn/Actor State。**

## 7. AI 架构

### 7.1 叙界在线

**AI 表现层：**叙事正文、对话、行动选项、开场方案、标题、摘要、小说章节、图片提示、可选 TTS。

**真实逻辑层：**JavaScript 对标签的解析、数值上下限、经验升级、快照、存储和 UI。

**【已确认】边界问题：AI 同时负责提出并决定大量真实状态。** `[STATE]` 可覆盖 HP/MP/地点/章节/职业/情绪；`[CHANGES]` 可改变物品、经验、技能、关系；任务和战斗结果也由 AI 输出。浏览器 d20 只作为文本发给 AI，伤害与敌方 HP 并非本地规则计算。因此在线玩法的“真实游戏逻辑层”并不完全独立。

### 7.2 Denova 游戏

**AI 表现层：**正文、候选行动、状态变化提案、导演更新提示、检定语义与后果描述。

**真实逻辑层：**冻结 schema、严格工具参数、状态字段类型、d20 投骰、状态绑定、父版本并发检查、终局规则、事件重放和原子落盘。

**【已确认】Denova 仍由 AI 判断“是否需要检定、难度和四档后果”，但随机结果和状态提交受后端约束。** 相比在线叙界，它更接近“AI 叙事 + 确定性规则内核”。

### 7.3 离线游戏

**【已确认】AI 只改写事件/结果文字并建议火柴人动作，不能改变数值、分支、战斗和结局；失败时自动回退固定文案。** 这是 AI 表现层和逻辑层分离最彻底的一条线。

## 10. 当前主要问题（客观存在）

### 严重

1. **【已确认】嵌入态场景预设会错误请求切换 Denova 模式。** `switchPreset()` 发送 `{presetId}`，而 `postToDenova('switch-scene')` 按不存在的 `payload.mode` 判断，结果除显式 `mode=game` 外都会请求 `ide`。玩家在叙界切预设可能被带离当前体验。
2. **【已确认】在线叙界的 AI 既写故事又写权威状态。** 标签格式错误、互相矛盾或幻觉会直接改变 HP、物品、任务、关系和战斗；`[STATE]` 还会覆盖前面已应用的 `[CHANGES]`。
3. **【已确认】同一产品存在三套不兼容的回合与规则真源。** 玩家在“叙界在线、Denova 游戏、叙界离线”之间不能延续同一游戏进度。

### 中等

4. **【已确认】Profile 与场景预设宣称本地持久化，但相关字段没有写入主存档 JSON。** 刷新后昵称、默认预设等不能可靠恢复。
5. **【已确认】离线游戏关闭或刷新后进度丢失。** 当前只有内存状态。
6. **【已确认】自动同步已经部署但当前没有实际同步索引。** 代码完成不等于当前用户数据已进入互通链路。
7. **【已确认】在线同步不是游戏状态同步。** 用户可能从“数据互通”措辞误以为任务/人物状态/战斗/分支也会互通。
8. **【已确认】项目文档存在现状冲突。** “纯静态单页、无后端”已不再准确；规划文档和已实施架构也有部分方向变化。

### 较低

9. **【已确认】叙界主脚本高度单体化且保留旧入口。** 小改动容易同时影响创建、存储、渲染和协议。
10. **【已确认】整体缺少统一版本号和 Git 历史。** 难以判断“当前整合版”相对 Denova 0.3.3 的精确差异。

## 11. 架构风险（未来可能出现）

1. **【推测】状态分叉风险：**标题/设定/章节可双向同步，但游戏状态各自独立，用户会形成“看起来是同一个冒险，实际上是多个副本”的认知冲突。
2. **【推测】同步备份膨胀：**Bridge 每次 push 前备份全部受管文件，叙界每次保存会调度 push；长期高频游玩可能产生大量 `.narraverse/backups`。
3. **【推测】存储膨胀：**在线快照保存完整对话历史，虽限制 24 个，但多冒险、角色卡和设定书仍会明显放大 IndexedDB。
4. **【推测】协议漂移：**在线标签协议、Denova 工具协议和同步 payload 同时演进时，缺少统一 schema 版本迁移会使旧数据逐渐难以兼容。
5. **【推测】维护回归：**`app.js` 全局状态和 DOM 直连、无正式同目录测试，功能继续增加后回归定位会越来越慢。
6. **【推测】可移植性风险：**桥接脚本硬编码 `<project-root>\denova\.denova`，当前机器可用，但目录再次移动会失效。
7. **【推测】产品定位风险：**写作工具、自由叙事、结构化 TRPG、固定离线游戏都在顶层出现，若没有明确主次，新玩家难以理解应从哪条线开始。

## 12. 建议优先级

### P0：必须先解决

1. **【建议】修复场景预设的宿主消息：**嵌入态 `presetId` 只重排叙界内部 UI，不应默认切到 Denova 写作模式；在协议明确前对 `switch-scene` 做 no-op。
2. **【建议】补齐 `userProfile/currentPresetId` 持久化并做一次迁移兜底。** 这是当前已经对外显示、但行为不符合预期的功能。
3. **【建议】明确三条游戏线的产品身份与状态真源：**建议把 Denova Game 定义为“结构化规则冒险”，叙界在线定义为“自由叙事冒险”，离线包定义为“无需 API 的试玩”；不要继续让三者看起来像同一存档的不同入口。
4. **【建议】把“当前同步范围”在 UI 明示为设定/素材/章节同步。** 避免玩家误判战斗和任务也会互通。

### P1：近期应该解决

1. **【建议】为叙界在线增加状态提交校验层：**先校验 schema、范围与互斥变化，再原子应用；至少禁止同轮 `[CHANGES]` 与 `[STATE]` 对同字段产生无提示覆盖。
2. **【建议】若要强化游戏性，优先复用 Denova 的后端 d20 与 Actor State，而不是继续扩展在线文本战斗协议。** AI 负责叙事，规则内核负责结果。
3. **【建议】建立最小跨模式 Adventure Identity：**先统一 `adventure_id/title/world/characters/lore/current_summary`，再决定是否映射任务和关系；不要直接尝试同步整套 Turn。
4. **【建议】为离线游戏增加本地存档，或把入口明确标为“单局试玩”。**
5. **【建议】给同步备份增加保留上限/按日合并，并显示最近同步状态与错误入口。**
6. **【建议】按 `storage / llm-protocol / game-state / wizard / sync / render` 拆分 `app.js`，先拆纯函数与协议层，不做全框架重写。**

### P2：后续优化

1. **【建议】在状态真源确定后再建设地图、时间、阵营、装备和经济。** 否则会在三套引擎中重复实现。
2. **【建议】统一整体版本号、CHANGELOG 与 Git 仓库，标明 Denova 基线版本和 Narraverse 自定义补丁。**
3. **【建议】清理 Legacy 函数、过时说明与重复规划文档，给“现状文档”和“未来规划”加明显状态标签。**
4. **【建议】最后再做跨模式视觉和动效深化；当前更影响体验的是规则与状态连续性，而不是皮肤细节。**

## 最终判断

**【已确认】叙界已经具备可玩的在线 AI 冒险、可审计的 Denova 结构化互动引擎、以及可离线通关的固定规则游戏。** 项目现在的主要矛盾不是“功能太少”，而是**功能已经很多，但三条游戏线的规则、状态与用户认知尚未统一**。

**【建议】下一阶段不要继续横向加系统。** 应先修复当前预设/持久化问题，明确三条线的主次和边界，再选择一套规则真源承接真正的“长期游戏进度”。
